# รอบคำถามผู้ซื้อ: ข้อตกลงข้อมูล

Status: accepted design under spec v0.16; implementation and runtime unverified
Version: 0.6
วันที่: 20 พ.ย. 2569
ต้นทาง: [intent](../brief.md), [spec](../spec.md), [ข้อมูลรายงาน](report-contract.md)

v0.6 ใช้กับสเปกรุ่นแข่ง v0.16 ที่ยอมรับคำถามหลายรอบและการกู้เคส ผลจากรอบซ้อมและตัวอย่างยังไม่ใช่ผลว่าแอปวันแข่งผ่านการตรวจ

## ขอบเขตและผลที่ต้องการ

ถามเฉพาะการตัดสินใจหรือการใช้งานที่ผู้ซื้อตอบได้และคำตอบเปลี่ยนการตรวจหรือคำแนะนำ ใช้ได้สูงสุด **3 รอบ รอบละ 1–5 ข้อ รวมไม่เกิน 15 ข้อในเส้นทางปัจจุบัน** ถ้าไม่มีคำถามให้จบและสร้างรายงาน ผู้ซื้อตอบบางข้อ ข้าม หรือไปที่รายงานได้ระหว่างรอบ

## การเลือกคำถาม

1. ใช้หลักฐานข้อความที่เกี่ยวข้องกับ SKU ที่ยืนยัน บริบท และคำถาม/คำตอบที่ออกและรับจริงใน revision ปัจจุบัน ไม่ส่งรูปในขั้นนี้ ข้อสังเกตจากรูปอยู่ในรายงานพร้อมข้อจำกัด
2. ค้นพบประเด็นจาก listing และคำตอบ ไม่ใช้แบบสอบถามตายตัว เก็บคำถามที่เคยข้ามไว้เพื่อไม่ถามซ้ำโดยอัตโนมัติ ไม่ถามเรื่องที่ทราบชัดแล้ว หากข้อมูลผู้ซื้อขัดกันและมีผลให้ถามเพื่อคลี่คลายได้
3. ถามหลายข้อพร้อมกันได้เมื่อคำตอบข้อหนึ่งไม่เปลี่ยนว่าอีกข้อควรถามหรือถามอย่างไร เช่น ความต้องการงานสกรีนกับการใช้ร้อน/เย็น คำถามที่พึ่งคำตอบ เช่น ยอมรับงานสกรีนสั่งทำหรือไม่ ให้รอรอบถัดไปและถามเมื่อ listing มีหลักฐานว่าเกี่ยวข้อง
4. เรียงตามผลต่อกรณีซื้อ รวมประเด็นร่วมของหลาย SKU ครั้งเดียว ไม่ซ่อนหลายเรื่องในข้อเดียว ไม่ถามให้ผู้ซื้อยืนยันเทคนิคผลิต ความปลอดภัย หรือข้อเท็จจริงสินค้า
5. ถ้าข้อมูลพอหรือไม่มีคำถามที่คุ้ม ให้คืนว่าจบรอบถาม สิ่งที่ยังไม่ทราบคงอยู่ในรายงาน ช่องว่างของหลักฐานไม่ได้หายเพราะไม่มีคำถาม

## Interface ของ Module ตรวจกรณีซื้อ

`QuestionInput` ภายใน Backend มี `case_id`, `revision`, `snapshot`, `selected_option_ids`, `buyer_context`, `answers` ที่ประกอบจากรอบที่ส่งแล้วตามลำดับ และ `round_number` ที่กำลังจะออก Backend จำกัดแหล่งข้อมูลเป็น source ที่เกี่ยวข้องและ available ตามแผน AI ตัวโมเดลคืน `{reason, questions}` โดย `questions` ยาว 0–5 รายการ Backend ตรวจ shape/scope และผูกผลกับ snapshot/revision ที่เรียก

- การส่งชุดคำถามสำเร็จมี `round_id`, `round_number` (1–3), `reason`, และ `questions` ที่ไม่ว่าง ผลเตรียมที่ไม่มีคำถามให้คืนเหตุผลและ `questions: []` Backend แสดง `ready_for_review` โดยไม่ออก round ใหม่ รวมกรณีข้อมูลพอตั้งแต่ต้น เมื่อส่งรอบ 3 ให้ไปต่อที่รายงานโดยไม่ขอรอบใหม่
- Question มี `question_id` (Backend กำหนดไม่ซ้ำในเคส รวมรอบที่ถูกแทน), `prompt`, `why_ask`, `option_ids`, `source_ids` และ `choices` เป็นคำตอบให้เลือกเพียงหนึ่งข้อหรือ `[]` สำหรับพิมพ์เอง ใช้ภาษาอังกฤษอ่านง่าย ไม่เลือกคำตอบแทนผู้ซื้อ
- `option_ids` เป็น subset ที่ไม่ว่างของ SKU ที่ยืนยัน `source_ids` อ้างเฉพาะ source ข้อความ available ที่ส่งจริงและตรง scope หากเป็นคำถามจากบริบทผู้ซื้อเพียงอย่างเดียวใช้ `[]` ได้ ข้อความต้นทางเกี่ยวกับ SKU หนึ่งไม่ยืนยันอีก SKU และห้ามอ้างข้อมูลจากภาพใน prompt/why_ask/choices
- `reason` และ `why_ask` เป็นคำอธิบายสั้นสำหรับผู้ซื้อ ไม่ใช้เป็นคำตัดสินสินค้าหรือคัดลอกบันทึกธุรกิจส่วนตัว คำถามหรือ output ผิด schema, เกินจำนวน หรืออ้างผิด scope คืน `invalid_questions` ไม่ตัดเงียบ ๆ หรือแปลงเป็นผลจบ

## ส่งคำตอบ แก้ไข และจบไปที่รายงาน

`submission = {round_id, answers}` โดย `answers` มี `{question_id, answer_text}` ครบทุกข้อที่ออกจริงครั้งเดียว Backend normalize ข้อความที่เป็น whitespace ล้วนเป็น `null` และเก็บคำตอบที่มีเนื้อหาตามต้นฉบับ ข้อที่ผู้ซื้อเว้นหรือกด **Not sure / Skip** ส่ง `null` การป้อนร่างหรือเลือกตัวเลือกกลางรอบยังไม่เรียกโมเดล Backend ไม่รับ `question_text`, snapshot, sources หรือ image path เพื่อประกอบคำถามหรือรายงานจาก client

- **Continue:** บันทึกคำตอบทั้งรอบก่อนเรียกโมเดลเพื่อขอคำถามถัดไป ถ้าถึงเพดานให้ขอรายงานต่อ ถ้าโมเดลตอบว่าไม่มีข้อที่ต้องถามแล้วให้ขอรายงานต่อเช่นกัน
- **View purchase review:** ส่งคำตอบที่กรอกในรอบที่เปิดพร้อมคำสั่งสร้างรายงาน ถ้าไม่มีรอบที่เปิดหรือแก้ไข ส่ง `submission: null` เพื่อใช้คำตอบที่บันทึกแล้ว ข้อมูลพอตั้งแต่ต้นใช้ path เดียวกันโดย answers ใน ReviewInput เป็น `[]` ตอนเกิดข้อผิดพลาดระหว่างเตรียมคำถาม ให้คงคำตอบและเปิดทาง Retry หรือ View purchase review
- **แก้คำตอบที่ส่งแล้ว:** แก้รอบที่ออกจริงในเส้นทางปัจจุบัน ถ้าคำตอบหลัง normalize เปลี่ยน ให้คงรอบก่อนหน้าและคำถามในรอบที่แก้ ตัดรอบหลังและรายงานที่ผูกกับคำตอบเดิม จากนั้นประเมินใหม่หรือขอรายงานทันทีตามปุ่มที่ใช้ ถ้าคำตอบไม่เปลี่ยน ให้เก็บรอบหลังไว้และใช้สถานะเดิม ไม่ออกคำถามซ้ำ
- Backend ประกอบ `ReviewInput.answers` จากรอบที่ยังใช้อยู่เท่านั้น ตามลำดับรอบและคำถาม เติม `question_text` จากคำถามที่ออกจริง คำตอบหรือบริบทเป็นข้อมูลจากผู้ซื้อ ไม่ใช้เป็นหลักฐานสินค้า คำตอบ `null` ไม่สร้าง requirement เงื่อนไขใหม่ที่ชัดใน scope เดียวกันแทนเงื่อนไขก่อนหน้าได้ เรื่องที่ขัดกันและยังไม่ชัดคงเป็น open preference พร้อมร่องรอยคำตอบที่เกี่ยวข้อง

ใช้ `case_id` คงที่สำหรับชุด snapshot/selection/context เดียวกัน และ `revision` เพิ่มเมื่อบันทึกคำตอบชุดใหม่หรือเปลี่ยนคำตอบ เปลี่ยน ZIP, SKU/ลำดับ หรือบริบทให้เริ่มเคสใหม่ การส่งซ้ำ การตรวจรหัสเก่า การกู้เคส และข้อผิดพลาดดู [integration plan](../integration-plan.md), [AI plan](../ai-execution-plan.md) ห้ามใช้ผลที่มาช้าของรอบหรือ revision เดิมกับเคสใหม่

## ตรวจจากตัวอย่าง

- บริบทเริ่มต้นครบ → ไม่มีช่องตอบ → ได้รายงานพร้อมช่องว่างของหลักฐานเดิม
- ตัวอย่างคำถามรอบแรกครอบคลุมลายและการใช้งานโดยอิสระ เมื่อเลือกว่าต้องสกรีน ให้รอบถัดไปพิจารณาว่ายอมรับงานสั่งทำเมื่อมีหลักฐานรองรับ เมื่อยอมรับภาพแปะแล้วให้ถามเรื่องอื่นที่จำเป็นหรือจบ
- ตอบบางข้อและส่งรายงานทันที → ใช้ข้อความที่ตอบและเก็บข้อที่ข้ามเป็น null ไม่มีคำถามรอบใหม่
- เปลี่ยนคำตอบรอบแรก → ไม่ใช้รอบที่สร้างจากคำตอบเดิม ผลที่ค้างหรือคำขอซ้ำไม่สร้างรอบซ้อน ตัวอย่าง JSON ใช้ใน test harness เท่านั้น และไม่ส่งคำตอบคาดหวังให้โมเดล
