# Purchase review: ข้อตกลงข้อมูล

Status: Phase 3 report contract for spec v0.16
Version: 0.11
วันที่: 21 พ.ย. 2569
ขอบเขต: ข้อตกลงข้อมูลที่ Module รายงานใช้และส่งกลับในรุ่นแข่ง ไม่ใช่คำสั่ง Build หรือ deploy
ต้นทาง: [spec](../spec.md), [intent](../brief.md)
ตัวอย่างรูปแบบเดิมสำหรับกรณีมี requirement และกรณีข้ามคำถาม: [report-contract-example.json](examples/report-contract-example.json)

ยอมรับเป็นส่วนหนึ่งของ [spec v0.15](../spec.md) วันที่ 19 พ.ย. ตาม [บันทึกการยอมรับ](../acceptance.md) การยอมรับ Design ไม่ใช่หลักฐานว่าแอปทำงานแล้วหรือคำสั่ง Build

## ผลที่ต้องการ

Frontend แสดงรายงานจากข้อมูลที่ได้รับได้โดยไม่ต้องตีความสินค้าใหม่ ฝั่งวิเคราะห์ผูกข้อสรุปกับความต้องการและหลักฐานได้ ฝั่งอ่าน ZIP ทราบว่าต้องรักษาข้อความ รูป ตัวเลือก และข้อมูลที่อ่านไม่ได้ไว้ให้ใครใช้ต่อ

เริ่มจาก Purchase review หลังผู้ซื้อยืนยันตัวเลือกและตอบหรือข้ามคำถามแล้ว รอบนี้ไม่ออกแบบ HTTP, การเก็บ session, วิธี parse ZIP, จำนวนครั้งเรียกโมเดล หรือการ deploy

## Interface ของ Module

| Module | รับ | คืน | สิ่งที่ต้องซ่อนไว้ใน Implementation |
| --- | --- | --- | --- |
| รับหลักฐาน | ZIP | `ListingSnapshot` | วิธีอ่าน HTML, mapping รูป, เส้นทาง archive และทรัพยากรที่ใช้ |
| ตรวจกรณีซื้อ | `ReviewInput` | `ReviewResult` | การตีความบริบท อ่านรูป ใช้เอกสารคัดไว้ จัดลำดับ และตรวจความสอดคล้องก่อนคืนผล |
| แสดงรายงาน | ผล `ready` พร้อม snapshot เดียวกัน | หน้ารายงานและข้อความที่ผู้ซื้อแก้ไข/คัดลอกได้ | การจัดวางและการเปิดหลักฐาน ไม่มีการเพิ่มข้อสรุปเอง |

เป็น Seam สำหรับแบ่งงาน ไม่ใช่ข้อกำหนดให้สร้าง service แยกหรือเพิ่ม framework รายละเอียดรอบสร้างคำถามอยู่ใน [question-contract.md](question-contract.md) ซึ่งประกอบร่องรอยคำตอบเข้ารูป ReviewInput ในเอกสารนี้ ไม่เพิ่มการตีความคำตอบฝั่ง Frontend

## ข้อมูลก่อนสร้างรายงาน

### ListingSnapshot

| Field | ความหมาย / ข้อกำหนด |
| --- | --- |
| `snapshot_id` | รหัสชุดหลักฐานเดียวกัน เปลี่ยนเมื่อเปลี่ยน archive หรือชุดหลักฐาน ไม่ใช้ item ID แทน snapshot |
| `title` | ชื่อสินค้าต้นฉบับที่อ่านได้ ไม่ใช่คำรับรองคุณสมบัติ |
| `options` | ตัวเลือกที่อ่านได้ แต่ละรายการมี `option_id`, `name_original`, `name_en`, `image_source_id` |
| `sources` | ข้อความและรูปจาก listing รวมทั้งเอกสารทางการที่คัดไว้ ใช้รหัสที่ตรวจย้อนกลับได้ |
| `limitations` | รายการสิ่งที่ขาด อ่านไม่ได้ หรือยังไม่ตรวจ พร้อมผลต่อการใช้ข้อมูล |

`name_en` เป็นคำแปลเพื่อให้เลือกสินค้าได้ ต้องผูกกลับชื่อเดิม ไม่ใช้คำแปลสร้าง SKU ใหม่ แต่ละตัวเลือกมี listing_text source ของชื่อ SKU เต็มที่ผูก option_id นั้นและ original_text ตรง name_original ให้ name_en ใช้ค่า text_en เดียวกับ source นี้ รวมถึง null เมื่อแปลไม่ได้ ไม่สร้างคำแปลคนละชุดระหว่างหน้าเลือกกับหลักฐาน ฝั่งรับหลักฐานต้องส่งข้อมูลพร้อมเลือกให้ frontend ได้ ส่วนการเรียกโมเดลแปลก่อนเลือกจะออกแบบในงานรับหลักฐาน ไม่กำหนดให้ parser แปลเอง

`title` เก็บชื่อจากส่วนสินค้าไว้ตามต้นฉบับ และมี listing_text source label คงที่ `Product title` ที่เก็บ original_text เดียวกันกับ text_en สำหรับชื่ออังกฤษ Frontend ใช้คำแปลจาก source นี้ ไม่แปลชื่อเอง หากแปลไม่ได้ให้แสดงต้นฉบับพร้อมข้อจำกัด

`image_source_id` อ้าง source ของรูปเฉพาะตัวเลือกที่ต้นทางระบุไว้ แม้ไฟล์หายหรืออ่านไม่ได้ โดย source คงสถานะ missing/unreadable และไม่เสิร์ฟ bytes ที่ไม่ผ่านตรวจ ใช้ `null` เมื่อไม่พบความสัมพันธ์กับรูปเฉพาะตัวเลือกเลย หากมีเพียงรูปสินค้ารวมให้ระบุที่ source label และอย่าแสดงเป็นภาพเฉพาะตัวเลือก หากแปลชื่อไม่ได้ให้คืน `null` พร้อม limitation และใช้ภาพ/ชื่อเดิมประกอบการยืนยัน โดยไม่เดาคำแปล

### Source

| Field | ความหมาย / ข้อกำหนด |
| --- | --- |
| `source_id` | รหัสไม่ซ้ำภายใน snapshot อ้างถึงชิ้นหลักฐานจริง ไม่ให้โมเดลสร้างแหล่งใหม่ |
| `kind` | `listing_text`, `listing_image` หรือ `official_guidance` |
| `label` | ชื่อส่วนของหน้าหรือเอกสารที่คนอ่านเข้าใจ |
| `option_ids` | ตัวเลือกที่ต้นทางผูกไว้ `[]` หมายถึงไม่ใช่หลักฐานเฉพาะตัวเลือก ไม่ได้ยืนยันว่าคุณสมบัตินั้นตรงทุกตัวเลือก |
| `availability` | `available`, `missing` หรือ `unreadable` |
| `original_text` | ข้อความต้นทางสำหรับแหล่งข้อความ ถ้าไม่มีหรืออ่านไม่ได้ใช้ `null` |
| `text_en` | คำแปลอังกฤษของ `original_text` ที่ฝั่งรับหลักฐานเตรียมไว้ ไม่ใช่ข้อสรุปสินค้า หากไม่มีคำแปลหรือเป็นรูปใช้ `null` |
| `image_file` | ชื่อหรือ locator ของภาพที่มีจริงสำหรับแหล่งรูป ถ้าไม่มีใช้ `null` |
| `url` | ลิงก์เอกสารทางการหรือต้นทางถ้ามี ใช้ `null` ได้ |

ข้อความต้นทางเก็บตามส่วนที่ใช้ เช่น ชื่อ SKU หรือคู่ชื่อคุณสมบัติ/ค่า โดยยังชี้ส่วนต้นทางได้ ไม่เก็บเป็นสรุปที่ลบคำจีนสำคัญทิ้ง Frontend ต้องเปิดข้อความหรือภาพที่ปลอดภัยจาก source นี้ ไม่รัน HTML/script จาก archive และไม่โหลดรูปภายนอกเพื่อกลบไฟล์ที่หาย

`text_en` ต้องรักษาขอบเขตและความไม่แน่นอนของต้นฉบับ Frontend แสดงต้นฉบับคู่คำแปลโดยระบุว่าเป็นคำแปล ไม่แปลใหม่เอง หากใช้ quote เพียงส่วนหนึ่งให้แสดงคำแปลทั้ง source พร้อมป้ายกำกับขอบเขต ไม่อ้างว่าทั้งคำแปลตรงกับ quote ย่อย หากคำแปลไม่มีให้ระบุข้อจำกัดแทนการเดา ข้อสังเกตจากภาพใน `image_observation` เขียนอังกฤษและแสดงเป็นการอ่านภาพ ไม่ใช้ `text_en` แอบยืนยันคุณสมบัติ

เอกสารทางการใน snapshot เป็นชุดที่ระบบคัดไว้ ไม่ใช่ไฟล์ที่อ้างว่าผู้ซื้ออัปโหลด ต้องติดป้ายให้ถูก และไม่ใช้ความเป็นแหล่งทางการยืนยันขอบข่ายบังคับใช้กับกระติกโดยอัตโนมัติ `image_file` ยังไม่ใช่ public URL วิธีเสิร์ฟภาพและการจำกัดไฟล์เลื่อนไปออกแบบงานรับหลักฐาน

ข้อมูล snapshot ที่มีคำแปลและ locator เป็นข้อมูลที่ Backend เป็นเจ้าของ Client ส่งกลับได้เพียงรหัส snapshot ไม่ส่งเนื้อหา source หรือ locator ให้ Backend เชื่อและโหลดใหม่ หาก snapshot หมดอายุ/ไม่ใช่ชุดปัจจุบันให้ invalid_input ตาม question-contract

### ReviewInput

| Field | ความหมาย / ข้อกำหนด |
| --- | --- |
| `case_id` | รหัสกรณีซื้อ คงเดิมใน snapshot/ตัวเลือก/บริบทชุดเดียวกัน |
| `revision` | ฉบับคำตอบที่ Backend บันทึก ใช้คู่กับ case_id เพื่อป้องกันผลเก่าทับผลใหม่ |
| `snapshot` | `ListingSnapshot` ที่ใช้ตรวจ |
| `selected_option_ids` | 1–3 รหัสไม่ซ้ำ ต้องอยู่ใน snapshot และมาจากการยืนยันผู้ซื้อ |
| `buyer_context` | บริบทที่ผู้ซื้อให้ ว่างได้ เป็นข้อมูลผู้ซื้อ ไม่ใช่หลักฐานสินค้าและไม่คัดลอกลงข้อความผู้ขายทั้งก้อน |
| `answers` | รายการ `{question_id, question_text, answer_text}` พร้อม `buyer_facet` หากระบุไว้ในคำถาม จากรอบที่ออกจริงและยังอยู่ในเส้นทางปัจจุบัน เรียงตามรอบและลำดับคำถาม รวมไม่เกิน 15 ข้อ `null` หมายถึงไม่ตอบ/ไม่ทราบ ใช้ `[]` หากไม่มีคำถาม |
| `answer_option_ids` | รหัสคำถามแต่ละข้อจับคู่กับ SKU ที่คำถามนั้นครอบคลุม Backend อ่านจากรอบที่ออกจริง รวมคำถามที่ข้ามด้วย |
| `requirements` | สถานะความต้องการที่ Backend คำนวณจากบริบทและรอบที่ยังมีผล พร้อมรหัส ข้อความ สถานะ SKU และที่มาของแต่ละการตัดสินใจ |

answers เป็นข้อมูลที่ผู้ซื้อบอกเช่นเดียวกับ buyer_context ไม่ใช้แทนหลักฐานยืนยันสินค้า แม้ผู้ซื้อจะเล่าว่าผู้ขายเคยยืนยันแล้ว Backend รับเฉพาะ revision ที่ตรงกับเคสปัจจุบันและประกอบจากข้อมูลที่บันทึกเอง

เมื่อผู้ซื้อเปลี่ยนวันสุดท้ายที่ต้องได้รับสินค้า ให้ใช้คำตอบล่าสุดเฉพาะ SKU ที่คำถามใหม่ครอบคลุม ถ้ารอบเก่าไม่มี `delivery_deadline` แต่คำถามระบุชัดว่าถามวันสุดท้ายที่ต้องได้รับสินค้า ให้ใช้กฎเดียวกัน คำตอบเรื่องวันส่งออกจากร้านหรือวันรับตัวอย่างยังใช้ได้ตามขอบเขตของคำถามนั้น

`Shared selector value` เป็น label ที่ importer กำหนดให้แหล่งข้อความค่ารองร่วม โดย option_ids ระบุชุดที่ต้นทางผูกไว้จริง ไม่ใช้ [] แทนความสัมพันธ์นี้ แหล่งที่ครอบคลุมหลายตัวเลือกอ้างได้เมื่อมีตัวเลือกที่เกี่ยวข้องในกรณีซื้อ ไม่ใช้ข้อมูลที่ใช้เฉพาะ SKU นอกชุดมารองรับชุดที่เลือก

Backend กำหนด A/B/C ตามลำดับ `selected_option_ids` และส่ง mapping นี้ให้ฝั่งวิเคราะห์ใช้ก่อนเขียนคำถามผู้ขาย Frontend ตาราง และ draft ใช้ mapping เดียวกันตลอดกรณีซื้อ ไม่ให้โมเดลกำหนดอักษรเอง ตัวอย่าง `[v0, v1, v6]` หมายถึง A=v0, B=v1, C=v6 หากเปลี่ยนลำดับต้องเริ่ม case ใหม่

Backend เติม question_text จากคำถามที่ออกจริงตาม [ข้อตกลงรอบคำถาม](question-contract.md) ไม่ส่งรอบที่ถูกแทนไปให้โมเดลรายงาน หลังแก้คำตอบหรือเปลี่ยนข้อมูลระบบต้องตรวจคู่ case_id/revision ก่อนคืนและแสดงผล

## ข้อมูลที่ส่งให้หน้ารายงาน

### การผูกข้อสังเกตกับหลักฐานในรายงานรุ่น 2

โมเดลส่ง `contract_version: 2` พร้อมรายการ `claims` และเลือก claim ที่เกี่ยวข้องให้แต่ละช่องเปรียบเทียบและข้อค้นพบ Backend เป็นผู้ประกอบหัวข้อ คำอธิบาย ตัวเลข และคำถามผู้ขายจากข้อมูลที่ตรวจแล้ว ข้อกำหนดของผู้ซื้อยังต้องอ้างข้อความจาก context หรือคำตอบรอบปัจจุบัน

- `claim_id` ชี้ข้อสังเกตหนึ่งรายการภายในรายงาน ส่วน `source_id` ชี้หลักฐานใน snapshot เดียวกัน ข้อสังเกตเฉพาะตัวเลือกมี `option_ids` เป็นรหัสตัวเลือกเดียว เช่น ชื่อของ A ต้องอ้าง source ชื่อของ A และ `quote` ต้องปรากฏใน `original_text` ที่ส่งจริง
- ข้อสังเกตจากภาพต้องอ้าง `image_source_id` ของตัวเลือกนั้น และรหัสภาพต้องอยู่ในชุดที่แนบกับคำขอจริง การอ่านหน่วยและตัวเลขจากภาพเป็นข้อสังเกตของโมเดล ผู้ซื้อเปิดภาพต้นฉบับเพื่อตรวจซ้ำได้ ตัวอย่างเช่น ข้อความ `316` ในชื่อ SKU กับ `750 ml` บนภาพเป็นคนละ claim และเปิดคนละหลักฐาน
- หลักฐานร่วมใช้ `option_ids: []` ที่ตัว claim และคงขอบเขตของ source ต้นฉบับไว้ ตารางแสดงหลักฐานที่ครอบคลุมตัวเลือกทั้งชุดผ่าน `shared_claim_ids` ส่วนข้อค้นพบที่เกี่ยวเพียงบางตัวเลือกต้องรักษาขอบเขตนั้นตามจริง
- เมื่อภาพหาย อ่านไม่ได้ หรือไม่ได้แนบ ให้ระบุข้อจำกัดผ่าน `unknowns` โมเดลส่ง claim เชิงยืนยันจากภาพนั้นไม่ได้ Backend ใช้รอบแก้ไขเดิมและคืน `invalid_review` หากผลยังใช้ไม่ได้

ตัวเลขพร้อมหน่วยต้องตรงกับหัวข้อที่ใช้อ้าง เช่น `720 ml` ใช้อธิบายความจุ แต่ใช้ยืนยันน้ำหนักไม่ได้ แต่ละช่องมี `limitations` สำหรับรูปของ SKU นั้น หากยังมีหลักฐานจากชื่อ ให้แสดงทั้งชื่อและสาเหตุที่ตรวจรูปไม่ได้ แต่ละกลุ่มใน `coverage` สรุปจากข้อมูลกรณีซื้อนั้น แม้ไม่มีข้อค้นพบ

เวลายกค่าจาก selector ต้องเก็บค่าที่บันทึกไว้ทั้งช่อง เช่น `720ml` การยกข้อความจากแหล่งอื่นต้องคงตัวเลขที่อ้างให้ครบ หากอ่านค่าความจุได้บนภาพ A ก็ระบุพร้อมกันไม่ได้ว่าค่าความจุบนภาพเดียวกันอ่านไม่ออก รูปของ B และหัวข้ออื่นบนรูป A ยังมีข้อจำกัดของตัวเองได้

เมื่อบันทึกสำเร็จ SQLite จะเก็บข้อมูลที่ใช้ประกอบรายงาน รุ่นของสัญญา รหัสหลักฐานข้อความและภาพที่ส่งจริง รวมถึงตัวรายงานใน transaction เดียวกัน เมื่อเปิดเคสอีกครั้ง Backend ตรวจเคส revision ลำดับ SKU และหลักฐานแล้วประกอบรายงานซ้ำโดยไม่เรียกโมเดล รายงานที่สร้างก่อนรุ่น 2 จะขึ้น **Regenerate report** ให้ผู้ซื้อเลือกสร้างใหม่ คำตอบ ลำดับ SKU และ snapshot เดิมยังอยู่ การเปิดหรือรีเฟรชหน้าไม่เริ่มสร้างรายงานเอง

### การใช้ความต้องการปัจจุบัน

Backend สร้าง `buyer_requirements` จากข้อที่มีสถานะ `active` ในเคส โมเดลรายงานอ้างรหัสเหล่านี้ได้เฉพาะในขอบเขต SKU ของข้อค้นพบ เมื่อแยกข้อกำหนดร่วมเพื่อแก้ค่าให้ A ระบบเก็บรหัสและแหล่งที่มาของค่าที่ยังใช้กับ B ไว้ด้วย รายการ `unresolved` แสดงให้ผู้ซื้อเห็น เรื่องที่ `waived` ยังเปิดดูที่มาได้ ข้อความถึงผู้ขายใช้เฉพาะคำถามและค่าที่ผูกกับข้อกำหนดที่ตรวจแล้ว เช่น วิธีทำลายหรือวันส่งมอบ

การแก้คำตอบรอบต้นจะคำนวณสถานะใหม่จากบริบทเดิมกับรอบที่เหลือ SQLite เก็บรายงานกับสถานะและหลักฐานของ revision เดียวกัน การเปิดรายงานที่สร้างด้วยสัญญาปัจจุบันใช้ข้อมูลในเครื่อง รายงานเก่าที่กู้ความสัมพันธ์ได้ชัดย้ายได้ในเครื่อง หากยังคลุมเครือให้ผู้ซื้อกด **Regenerate report** แล้วตรวจประเด็นที่ยังเปิดอยู่ โดยเก็บตัวเลือกและคำตอบเดิมไว้

### ReviewResult

- สำเร็จ: `{status: "ready", report: PurchaseReview}`
- ไม่ได้ผลที่ใช้ได้: `{status: "failed", case_id, revision, code, message}`
- `code` ใช้ `invalid_input`, `analysis_failed` หรือ `invalid_review` สำหรับปัญหาข้อมูลตั้งต้น การวิเคราะห์ล้มเหลว หรือผลวิเคราะห์ไม่ผ่านการตรวจ ตามลำดับ ไม่ส่งรายงานที่ไม่ครบเป็น `ready`

การไม่มีข้อค้นพบเป็นผลที่เป็นไปได้ ต้องยังอธิบาย coverage และข้อจำกัด ไม่แปลว่าอนุมัติให้ซื้อหรือปลอดภัย

### PurchaseReview

| Field | ความหมาย / ข้อกำหนด |
| --- | --- |
| `contract_version`, `claims` | รุ่น 2 พร้อมข้อสังเกตที่ผ่านการตรวจและข้อความที่ Backend ประกอบสำหรับแสดงคู่หลักฐาน |
| `case_id`, `revision`, `snapshot_id` | ตรง input ฉบับที่ใช้วิเคราะห์ Frontend แสดงเฉพาะผลของเคสและ revision ปัจจุบัน |
| `selected_option_ids` | ตรงกับตัวเลือกที่ยืนยัน ไม่ให้โมเดลเพิ่ม/สลับตัวเลือก |
| `buyer_requirements` | ข้อกำหนดที่ผู้ซื้อให้จริง แต่ละรายการมี `requirement_id`, `text`, `input_ref`, `quote`, `option_ids` และ `question_text` |
| `open_preferences` | รายการ `{preference_id, text, input_refs, finding_ids, option_ids, questions}` สำหรับเรื่องที่ยังไม่ทราบหรือความต้องการขัดกัน ไม่ตีความว่าไม่มีข้อกำหนด |
| `comparisons` | ประเด็นที่ใช้เทียบตัวเลือก แต่ละรายการมี `label`, `shared_claim_ids`, `values` โดย value มี `option_id`, `claim_ids`, `summary`, `source_ids` แสดงทุกตัวเลือกที่ยืนยันหนึ่งครั้งต่อประเด็น ไม่จัดอันดับความปลอดภัย |
| `findings` | ข้อค้นพบระบุ `claim_ids` และเรียงจากสิ่งที่ควรจัดการก่อน ไม่บังคับจำนวนเป็น 3 |
| `coverage` | สถานะของ 3 กลุ่ม พร้อมเหตุผลและข้อค้นพบที่เกี่ยวข้อง |
| `limitations` | ขอบเขตรายงานและสิ่งที่ยังตรวจไม่ได้ รวมข้อจำกัด input ที่ยังมีผลต่อรายงาน |
| `supplier_draft` | ข้อความเริ่มต้นให้แก้ไข/คัดลอก สร้างจากคำถามผู้ขายใน findings ตามลำดับ ไม่ใช่ข้อความส่งจริง |

Backend ตรวจ `quote` กับคำตอบเต็ม หรือประโยคหรือบรรทัดเต็มจากบริบทเริ่มต้นตาม `input_ref` เพื่อรักษาคำปฏิเสธและเงื่อนไข คำตอบสำหรับ A ใช้กำหนดคำถามผู้ขายเกี่ยวกับ A ได้เท่านั้น หน้ารีวิวแสดงคำถามที่ออกจริงและ SKU ที่เกี่ยวข้อง ข้อความถึงผู้ขายใช้หัวข้อและเงื่อนไขที่รองรับ เช่น ต้องการหรือไม่รับงานสกรีน หากความต้องการยังคลุมเครือให้ถามกลาง ๆ ข้อมูลส่วนตัวในบริบทผู้ซื้อยังอยู่เฉพาะฝั่งผู้ซื้อ

`open_preferences.input_refs` เป็นรายการ `context` หรือ `answer:<question_id>` อ้าง `answer:<question_id>` ของคำถามที่ถามจริงแต่ answer_text เป็น null ได้ เพื่อบอกว่าความต้องการเรื่องนั้นยังเปิดอยู่ ใช้ `[]` เมื่อไม่ได้ถามและ context ไม่กล่าวถึงเรื่องนั้น การอ้างคำตอบ null ไม่สร้าง buyer requirement ส่วน `finding_ids` อ้างข้อค้นพบที่มีจริง ใช้ `[]` ได้เมื่อไม่มีข้อค้นพบเกี่ยวข้อง ทุก finding ที่ `action_type: decide_preference` ต้องมี open preference อ้างถึงอย่างน้อยหนึ่งรายการ

เมื่อคำตอบรอบคำถามเปลี่ยนความต้องการจาก context อย่างชัดเจนสำหรับขอบเขตเดียวกัน ให้ใช้คำตอบนั้น เช่น “Screen printing is required” ตามด้วย “Any finish is acceptable” ไม่คง requirement สกรีน หากยังตีความไม่ได้ว่าเปลี่ยนใจจริงหรือเป็นคนละขอบเขต ให้เก็บทั้งสอง input refs ใน open preference และไม่สร้าง requirement ที่ตัดสินแทนผู้ซื้อ ไม่เพิ่มรอบคำถามเกินขอบเขตเดิม

ติดตามเงื่อนไขตามเรื่องที่ถามและ SKU ที่ครอบคลุม เช่น “Screen printing is required” กับ “A matte finish is required” ใช้พร้อมกันได้ทั้งคู่ หากผ่อนเงื่อนไขของ A ให้แก้เฉพาะ A และเก็บความต้องการเดิมของ B ไว้ตามคำตอบที่ออกจริง

Backend เติมรหัสกรณีซื้อ/ชุดหลักฐานจาก input ที่รับไว้ ไม่ให้โมเดลกำหนดรหัสเหล่านี้เอง หากไม่มีคำถามผู้ขายให้ `supplier_draft` เป็นข้อความว่างและไม่แสดงปุ่มคัดลอกข้อความเปล่า หากมีคำถาม ให้เรียงเลขตามคำถามที่มีจริงหลังตัดรายการ `null` แล้ว

### การแสดงผลหลังถามหลายรอบ

เปิดด้วย **Before you order** จัดประเด็นตามผลต่อการซื้อ แต่ละประเด็นแสดงเงื่อนไขจากคำตอบที่เกี่ยวข้องผ่าน requirement_ids ผลจากหลักฐาน และสิ่งที่จะยืนยันต่อ ข้อค้นพบจากหลักฐานที่ผู้ซื้อไม่ได้กล่าวถึงยังแสดงได้โดยไม่เดาความต้องการ **Compare selected options** ใช้ตารางเดิมและแสดงประเด็นร่วมครั้งเดียว ส่วน **Message to supplier** ใช้ draft เดิมที่แก้และคัดลอกได้ Coverage ทั้งสามกลุ่มและข้อจำกัดต้องยังเปิดดูได้

เมื่อคำตอบเปลี่ยน งานที่ผู้ซื้อต้องทำและข้อความถึงร้านต้องปรับตาม เช่น สำเร็จรูปเท่านั้นให้ถามวิธีทำลายของ SKU นั้น ยอมสั่งทำให้เพิ่มทางเลือกสอบถามการสกรีนสั่งทำเมื่อ listing รองรับตัวเลือกนี้ การรับสั่งทำของร้านยังไม่ยืนยันวิธีทำลายของ SKU สำเร็จรูป

### Finding

| Field | ความหมาย / ข้อกำหนด |
| --- | --- |
| `finding_id`, `title` | รหัสไม่ซ้ำและหัวข้อที่สรุปได้เท่าหลักฐาน |
| `option_ids` | ตัวเลือกที่ได้รับผล ไม่ว่างและเป็น subset ของตัวเลือกที่ยืนยัน ประเด็นร่วมใส่ทุกรหัสที่เกี่ยวข้องแล้วแสดงครั้งเดียว |
| `kind` | `listing_conflict`, `requirement_unconfirmed`, `clarification_needed` หรือ `evidence_gap` เป็นชนิดประเด็น ไม่ใช่ระดับความร้ายแรง |
| `action_type` | `decide_preference`, `ask_supplier` หรือ `request_evidence` ใช้จัดงานต่อ ไม่เพิ่มรอบคำถามผู้ซื้อ |
| `requirement_ids` | ข้อกำหนดผู้ซื้อที่เกี่ยวข้อง ใช้ `[]` ได้เมื่อเป็นประเด็นที่ระบบค้นพบเอง |
| `citations` | หลักฐานที่ใช้ แต่ละรายการมี `source_id`, `quote`, `image_observation` |
| `interpretation` | สิ่งที่ระบบตีความจากหลักฐาน แยกจากข้อความต้นทาง |
| `impact` | ผลต่อกรณีซื้อโดยอิงความต้องการที่มีจริง |
| `priority_reason` | เหตุผลที่จัดลำดับนี้ ไม่ใช่คะแนนความมั่นใจ |
| `unknowns` | สิ่งที่ยังไม่ทราบ แต่ละรายการมี `text`, `reason`, `source_ids` |
| `requested_evidence` | ข้อมูลหรือหลักฐานเฉพาะที่ช่วยประเมินต่อ ไม่เขียนเพียงให้ถามผู้ขาย |
| `evidence_limits` | หลักฐานที่ขอยังพิสูจน์อะไรไม่ได้ ไม่ถือคำตอบผู้ขายเป็นการตรวจสินค้าจริง |
| `supplier_question` | คำถามสินค้า/หลักฐานที่นำไปประกอบข้อความผู้ขาย ใช้ `null` ได้หากมีเพียงการตัดสินใจของผู้ซื้อ |

แหล่งข้อความต้องมี `quote` ตรงกับข้อความต้นทางและ `image_observation: null` แหล่งรูปใช้ `quote: null` และระบุสิ่งที่อ่านจากรูปใน `image_observation` การตรวจ source ID หรือ quote ผ่านไม่ใช่ verified และไม่พิสูจน์ภาพอ่านถูก

`unknowns.reason` ใช้ `not_found`, `not_reviewed` หรือ `unreadable` ตามลำดับ: ไม่พบข้อมูลในส่วนที่อ่านและตรวจแล้ว, มีแหล่งที่อ่านได้แต่ยังไม่ได้ตรวจ, หรือใช้แหล่งนั้นไม่ได้เพราะไฟล์หาย/อ่านไม่ได้ ให้ text ระบุสาเหตุจริง เช่นไฟล์ missing/decode ไม่ได้ หรือข้อความในภาพไม่ชัด แม้ decoder เปิดภาพและ Source ยัง available ได้ ไม่เปลี่ยน availability เพียงเพราะอ่านข้อความไม่ได้ ไม่ใช้ not_found สื่อว่าอ่านภาพที่หายแล้วไม่พบข้อความ `source_ids` ระบุขอบเขตที่ใช้กล่าวเช่นนั้น ไม่แปล `not_found` ว่าไม่มีสิ่งนั้นในสินค้าหรือโลกจริง

ข้อค้นพบต้องแยกไม่พบข้อมูลรายงานทดสอบออกจากพบข้อความผู้ขายว่าไม่มีรายงาน เช่นเดียวกับการยังไม่อ่านรูปต้องไม่กลายเป็นไม่มีข้อความในรูป แหล่งที่ `missing`/`unreadable` ใช้อธิบายข้อจำกัดใน `unknowns` ได้ แต่ใช้เป็น citation อ้างว่าเห็นข้อความหรือภาพนั้นไม่ได้ กฎเดียวกันใช้กับ `comparisons[].values[].source_ids` ซึ่งรับเฉพาะ source ที่ `available` หากภาพหายให้ summary บอกว่าตรวจภาพไม่ได้ ไม่อ้างความจุจากรูปนั้นและไม่ใส่ source ที่หายเป็นหลักฐานข้อกล่าวอ้าง

citations และ comparisons ใช้ได้เฉพาะเนื้อหา source ที่ available และ Backend ส่งให้ขั้นรายงานจริง รูปที่มีเพียง metadata ยังใช้ยืนยันข้อความในภาพไม่ได้ ส่วน unknowns อ้าง metadata ของแหล่งที่ไม่ได้ส่ง/ไฟล์หายได้เพื่อบอกข้อจำกัด โดยรักษา scope ของตัวเลือก

### Coverage

คืน 3 รายการเสมอ แต่ละรายการมี `group`, `status`, `finding_ids`, `note`

| ค่า | ความหมาย |
| --- | --- |
| `group: product_match` | สินค้าและตัวเลือกเทียบความต้องการ |
| `group: intended_use` | สิ่งที่ควรตรวจตามการใช้งาน |
| `group: supporting_evidence` | ความเพียงพอของหลักฐานรองรับ |
| `status: reviewed` | พิจารณาข้อมูลที่มีแล้ว ไม่ใช่สถานะผ่าน |
| `status: limited` | พิจารณาได้บางส่วน ต้องบอกว่าขาดอะไร |
| `status: not_assessed` | ยังประเมินกลุ่มนี้ไม่ได้ ต้องบอกเหตุผล |

แม้ `findings: []` ยังต้องคืน coverage ทั้ง 3 กลุ่มพร้อม `note` ว่าพิจารณาอะไรและขาดอะไร ไม่ใช้คำว่า reviewed เป็นไฟเขียว

`finding_ids` อ้างรหัสที่มีจริง ใช้ `[]` ได้ หนึ่งข้อค้นพบอยู่หลายกลุ่มได้ เช่น วัสดุเกี่ยวกับทั้งการใช้งานและข้อมูลรองรับ ไม่ทำสำเนาข้อค้นพบแยกตามกลุ่ม

## ความรับผิดชอบก่อนคืนผล

1. ฝั่งรับหลักฐานเป็นเจ้าของรหัส source/option และข้อมูลต้นทาง ฝั่งวิเคราะห์เลือกใช้อ้างอิงแต่ไม่เปลี่ยนต้นฉบับ
2. ฝั่งวิเคราะห์ตรวจรหัส จำนวนตัวเลือก การอ้าง scope และ quote รวมทั้งตรวจความหมายของข้อสรุปกับหลักฐาน แยกการตรวจโครงสร้างออกจากการตรวจคุณภาพคำตอบ
3. เมื่อวิเคราะห์เสร็จ Backend ประกอบ `supplier_draft` จากชื่อ SKU เดิมกับ `supplier_question` ตามลำดับ findings ไม่เรียกโมเดลใหม่เพื่อแต่งข้อความทั้งก้อน และไม่แนบ buyer context โดยตรง คำถามแต่ละข้อยังต้องตรวจว่าไม่ใส่บันทึกธุรกิจที่ไม่เกี่ยวข้อง
4. Frontend แสดงต้นฉบับ/คำแปล/ข้ออนุมานตามชนิดข้อมูล ไม่เติมข้อกล่าวอ้างเอง ไม่ทำคะแนนหรือไฟเขียวจาก coverage ที่ `reviewed`
5. ข้อความที่ผู้ซื้อแก้เป็นฉบับสำหรับคัดลอก ไม่ย้อนแก้ findings เมื่อเริ่มตรวจกรณีซื้อใหม่ต้องแจ้งว่าจะสร้าง draft ใหม่ ไม่เอาข้อความเดิมไปใช้กับ SKU ใหม่เงียบ ๆ
6. เมื่อเปลี่ยนชุด snapshot/selection/context ให้ใช้ case_id ใหม่ เมื่อบันทึกคำตอบต่างจากเดิมให้เพิ่ม revision และล้างรายงานเก่า ผลจาก case_id/revision เดิมต้องไม่แสดงเป็นผลปัจจุบัน

ฟิลด์คำอธิบายอย่าง `impact` และ `priority_reason` แสดงเป็นข้อความธรรมดา โดย impact ใช้ในรายละเอียดและ priority_reason ใช้ในสรุปลำดับ `kind` ใช้แสดงชื่อชนิดประเด็นเท่านั้น ไม่สร้างกฎคะแนนหรือ flow แยกตามทุก field คงความต่างของข้อมูลไว้จนมีผลทดลองโมเดลจริงให้ประเมินการตัด field

## ตัวอย่างการเชื่อมข้อมูล

กรณีใน JSON เลือกสามตัวเลือกจากเคสจริง แต่บริบทและคำตอบผู้ซื้อเป็นข้อมูลสมมติสำหรับอธิบาย Interface: ต้องการสกรีน ต้องการ 720 ml และใช้กับเครื่องดื่มร้อน มีบันทึก margin ที่ต้องไม่ติดไปกับข้อความผู้ขาย

- requirement งานสกรีนอ้างกลับ `answer:q-finish`
- finding เรื่องลายอ้างชื่อตัวเลือกทั้งสามและเมนูปรับแต่งระดับสินค้า จึงสรุปเพียงยังไม่ยืนยัน requirement
- finding ความจุอ้าง selector และภาพของตัวเลือกที่ทีมตรวจไว้ ไม่สรุปความจุสินค้าจริง
- finding วัสดุอ้างข้อมูลที่ผู้ขายระบุและบอกส่วนที่ไม่พบ ไม่สรุปว่า PP หรือการไม่มีรายงานแปลว่าไม่ปลอดภัย

`additional_examples` ใน JSON เป็นรูปแบบ fixture สำหรับเอกสารเท่านั้น: ใช้สำเนา `input` หลักแล้วแทน field ระดับบนตาม `input_overrides` จึงใช้ snapshot เดียวกันโดยไม่ทำสำเนา ส่วน `expected_result` เป็นผลครบของกรณีนั้น ไม่ใช่การเพิ่ม field ให้ ReviewInput ตัวอย่างที่สองใช้บริบทเพียงนำมาขายและข้ามทั้ง 3 คำถาม แสดง open preferences และข้อค้นพบที่ไม่มี requirement ผู้ซื้อกำกับ

JSON เป็นตัวอย่างที่เขียนขึ้น ไม่ใช่ผลอ่าน ZIP หรือผลจากโมเดล ภาพ 750 ml อิงการตรวจด้วยสายตาของทีม ตัวอย่าง skip ใช้ IDs/prompt เดียวกับ linked-skip ใน question fixture ส่วนตัวอย่างมี requirement แสดง input หลังตอบแยกต่างหาก ใช้แสดงรูปแบบรายงานหลังตอบ วิธีโหลด/serve ภาพและชุดอ้างอิงรุ่นแรกเสนอไว้ใน integration-plan แล้ว ยังต้องตรวจด้วยแอปจริง

## เกณฑ์ตรวจร่างและการตรวจตอน Build

| จุดตรวจ | สิ่งที่ต้องยืนยัน |
| --- | --- |
| ความครบของรายงาน | ทุก field จำเป็นมีค่า/รายการว่างตามที่กำหนด มี coverage 3 กลุ่มและเหตุผลข้อจำกัด |
| การอ้างอิง | ไม่มี source, option, requirement หรือ finding ที่ไม่มีจริง ไม่มี citation ไปยังไฟล์ที่อ่านไม่ได้ |
| ความต้องการ | quote มาจากผู้ซื้อจริง ไม่แต่ง requirement จากรูปหรือข้อความผู้ขาย |
| ความหมาย | เมนูสกรีนไม่เท่ากับ SKU สกรีน ตัวอักษรไม่เท่ากับวิธีพิมพ์ คำอ้างวัสดุไม่เท่ากับผลทดสอบ |
| ข้อมูลขาด | รูปหาย/ยังไม่ตรวจ/ข้อความไม่พบให้ผลต่างกันอย่างถูกต้อง |
| ความเป็นส่วนตัวของ draft | ไม่มี buyer context ทั้งก้อนหรือบันทึกภายในที่ไม่เกี่ยวข้อง มีชื่อ SKU ที่เลือกและลำดับคำถามตรงรายงาน |
| ผลเก่าและ error | ผลคนละ case หรือ revision ไม่แทนผลใหม่ ผลวิเคราะห์ไม่ครบไม่แสดงเป็นสำเร็จ |

รอบ Design ตรวจได้เพียง JSON ความสอดคล้องและขอบเขตของตัวอย่าง การทดสอบ endpoint, โมเดลจริง, latency, ต้นทุน และรีวิว Standards/Spec ของโค้ดจริงยังอยู่ใน Build/Test ไม่ถือว่าผ่านจากเอกสารนี้
