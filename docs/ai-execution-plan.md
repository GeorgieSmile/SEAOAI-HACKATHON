# แผนเรียก AI และเลือกโมเดล

เดโม Railway ใช้ OpenAI Responses API กับ `gpt-6.1-terra` ที่ reasoning effort `medium` ทั้งงานแปล คำถาม และรายงาน ดู [ผลตรวจรุ่นที่ deploy](../plans/purchase-04-integrate-and-verify/verification.md#railway-release-checks)
Version: 0.6
วันที่: 20 พ.ย. 2569
ต้นทาง: [intent](brief.md), [spec](spec.md), [รับ ZIP](contracts/intake-contract.md), [รอบคำถาม](contracts/question-contract.md), [รายงาน](contracts/report-contract.md)

ยอมรับเป็นส่วนหนึ่งของ [spec v0.15](spec.md) วันที่ 19 พ.ย. ตาม [บันทึกการยอมรับ](acceptance.md) การยอมรับ Design ไม่ใช่หลักฐานว่าแอปทำงานแล้วหรือคำสั่ง Build

## ข้อเสนอเริ่มต้นก่อนแข่ง

เริ่มทดสอบ API ด้วย `gpt-6.1-terra` ที่ reasoning effort `medium` เป็นโมเดลเดียวทั้งเส้นทาง หากงานใดยังไม่ผ่านหลังตรวจ prompt/ข้อมูล ให้เทียบ `gpt-6.2-sol` เฉพาะงานนั้นก่อนเลือกใช้ในงานแข่ง เหตุผลเริ่มจาก Terra คือความสามารถที่รองรับและต้นทุนตามเอกสาร ไม่ใช่หลักฐานว่าดีกว่า Sol

ผล screening เดิมเป็นการทดลองผ่าน Codex ไม่ใช่ API benchmark และอาจเห็นตัวอย่าง จึงยังต้องตรวจโมเดลจริงตามเกณฑ์ด้านล่าง

ใช้ OpenAI Responses API กับ structured outputs สำหรับผลที่ต้องแปลงเป็นข้อมูล ไม่เพิ่ม agent framework, tools, web search, vector database หรือโมเดลตรวจโมเดลอีกชั้น เอกสารทางการที่คัดไว้ส่งเป็นข้อความต้นฉบับพร้อมรหัสและข้อจำกัด ไม่ให้โมเดลค้นข้อบังคับเอง

## โมเดลที่พิจารณาก่อนแข่ง

ราคาด้านล่างเป็น Standard processing สำหรับ short context ต่อ 1 ล้าน tokens ตามหน้าโมเดลที่ตรวจวันที่ 18 พ.ย. 2569 ไม่รวม cache discount หรือบริการเสริม และไม่ใช่ต้นทุนที่วัดจากแอป

| โมเดล | Input / Output | บทบาทที่เสนอ | หลักฐานรอบนี้ |
| --- | --- | --- | --- |
| `gpt-6.1-terra` | $1 / $5 | ตัวเต็ง ใช้ทั้งแปล คำถาม และรายงานก่อน | ทดลองผ่าน Codex ที่ medium บันทึก screening ไม่รวมในชุดนี้ ไม่ใช่ผลทดสอบ API |
| `gpt-6.2-sol` | $2 / $10 | ตัวเทียบด้านคุณภาพ หาก Terra ไม่ผ่านเกณฑ์ | ทดลองผ่าน Codex ที่ medium บันทึก screening ไม่รวมในชุดนี้ ไม่ใช่ผลทดสอบ API |
| `gpt-6-luna` | $0.10 / $0.50 | พิจารณาเฉพาะแปล/งานจำกัดขอบเขตเมื่อจำเป็นต้องลดต้นทุน | ตรวจเอกสาร ยังไม่ได้ทดลอง |
| `gpt-6.2-astra` | $8 / $40 | สำรองสำหรับหาสาเหตุของเคสยาก ไม่เสนอเป็นค่าเริ่มต้น | ตรวจราคา ยังไม่ได้ทดลอง |

Terra และ Sol รองรับภาพกับ structured outputs ตามเอกสาร OpenAI ณ วันที่จัดทำแผน ทีมยังไม่ได้ตรวจสิทธิ์ API ของบัญชีนี้ ราคาและความสามารถมาจาก [Terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra), [Sol](https://developers.openai.com/api/docs/models/gpt-6.2-sol), [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) และ [pricing](https://developers.openai.com/api/docs/pricing)

## เรียกโมเดลเมื่อไร

เมื่อนำเข้าลิงก์หรือ ZIP ใหม่ ระบบขอคำแปล 1 ครั้ง เตรียมคำถาม 1–3 ครั้งตามจำนวนรอบ และสร้างรายงาน 1 ครั้งหลังผู้ซื้อยืนยัน brief รวม 3–5 ครั้งสำหรับเส้นทางนี้ก่อนนับการลองใหม่ การแก้คำตอบ และการ preview ข้อความแก้ brief

ถ้าผู้ซื้อเขียนคำตอบเอง backend จะตีความในเครื่องก่อน เมื่อยังมีคำตอบที่ต้องให้โมเดลช่วย ระบบรวมคำตอบเหล่านั้นไว้ในคำขอเดียว เพิ่มได้สูงสุด 1 ครั้งต่อรอบ ถ้ายังตีความไม่ได้ ระบบขอให้ผู้ซื้อระบุให้ชัดหรือเว้นข้อนั้นไว้ การพิมพ์คำตอบและการเปิดเคสเดิมใช้ได้โดยไม่เรียก AI เดโมสาธารณะไม่มีเพดานจำนวน API requests สะสมต่อเบราว์เซอร์หรือทั้งระบบ

| ขั้น | ข้อมูลที่ส่ง | งาน AI | งานของโค้ด |
| --- | --- | --- | --- |
| 1. เตรียมคำแปล หลังนำเข้าลิงก์หรือ ZIP | ชื่อสินค้า ชื่อตัวเลือกทั้งหมดและข้อความสินค้าที่ parser อนุญาต พร้อม source/option IDs | คืน `name_en` และ `text_en` เป็นอังกฤษ รวม Product title source โดยไม่เปลี่ยน title ต้นฉบับโดยรักษาขอบเขตและความไม่แน่นอน | อ่าน archive/DOM, ผูกภาพ, ตรวจ ID, รักษาต้นฉบับ, เก็บคำแปลใน snapshot และนำ text_en ของ source ชื่อ SKU มาเติม name_en ไม่ให้สองหน้ามีคำแปลต่างกัน |
| 2. เตรียมคำถาม หลังยืนยันหรือส่งคำตอบ | ข้อความของ SKU ที่เกี่ยวข้อง บริบท คำถาม/คำตอบที่บันทึก แล้วเอกสารคัดไว้ที่เกี่ยวข้อง | คืนเหตุผลและคำถามรอบถัดไป 0–5 ข้อ ถ้าไม่มีให้จบ | ตรวจรหัส/scope/เพดาน 3 รอบ บันทึกรอบที่ออกจริง ไม่ส่งรูป |
| 3. สร้างรายงาน หลังยืนยัน buying brief | ต้นฉบับ/คำแปล ชุดรูปที่เลือกส่ง และข้อกำหนดตาม SKU ของ revision ที่ยืนยัน | คืนเนื้อหารายงานและ supplier questions ตาม contract | ตรวจผล เติมรหัสจาก input และประกอบ supplier draft ตามลำดับ findings |

เมื่อขั้น 2 คืน 0 คำถาม ให้แสดง buying brief ทันที ขั้น 3 จะเริ่มเมื่อผู้ซื้อยืนยัน revision ที่แสดงเท่านั้น

เมื่อผู้ซื้อกด preview ข้อความแก้ brief ที่มี scope และความหมายพอตรวจได้ ระบบใช้ client เดียวกับขั้นคำถามเพื่อขอข้อเสนอแบบมีโครงสร้าง ตรวจข้อความเดิม วันของถึง และรหัส SKU ก่อนแสดงผล การเปิด brief การบันทึกผล preview การ Undo และการกู้เคสใช้ข้อมูลที่ตรวจใน backend แล้ว การยืนยันเรียกเฉพาะขั้นสร้างรายงาน

เก็บคำแปลใช้ซ้ำเฉพาะ snapshot เดิม ไม่แปลซ้ำเมื่อเปลี่ยนตัวเลือกหรือกู้เคส เปลี่ยน SKU/ลำดับ/context ให้เริ่มเคสใหม่ แก้คำตอบรอบก่อนให้ใช้ revision ใหม่และประเมินจากคำตอบที่ยังมีผล ถ้าผู้ซื้อจบคำถามก่อน ให้ใช้คำตอบที่บันทึกแล้วประกอบ brief เพื่อรอยืนยัน

ใช้โมเดลเดียวก่อนเพื่อลดสิ่งที่ต้องทดสอบ หาก Terra ผ่านงานแปลและคำถามแต่รายงานไม่ผ่าน ให้ลองเปลี่ยนเฉพาะรายงานเป็น Sol แล้วทดสอบเส้นทางผสมนั้นจริงก่อนใช้ ไม่ให้โมเดลเลือก route เอง และไม่สลับโมเดลเงียบ ๆ เมื่อ error ไม่เพิ่มตัวเลือกโมเดลในหน้าแอป

### แนวทางสำหรับ prompt แปลและคำถาม

ตั้งแต่ PR #16 การแปลใช้ประเภทสินค้าและชื่อ field ช่วยตีความ โดยเก็บรายละเอียดตามข้อความของแต่ละ SKU เช่น “with an applied picture” บอกว่ามีภาพติดบนตัวสินค้า คำว่า “with picture” ทำความหมายเรื่องการติดภาพหายไป จะระบุชนิดกาว วัสดุ หรือวิธีผลิตได้ต่อเมื่อต้นฉบับของรายการนั้นระบุไว้ รายการวิธีปรับแต่งที่ร้านรับทำใช้ยืนยันวิธีผลิตของ SKU ใด SKU หนึ่งไม่ได้ ดู [prompt ที่ใช้จริง](../backend/prompts/translate-listing-v1.txt)

- **แปล:** ใช้ภาษาอังกฤษสั้นและอ่านง่ายสำหรับผู้ซื้อที่อาจไม่คล่องภาษา คงวัสดุ ตัวเลข หน่วย เงื่อนไข คำปฏิเสธ และความกำกวมของต้นฉบับ ใช้ศัพท์เทคนิคเมื่อจำเป็นต่อความหมาย ชื่อ SKU เป็นป้ายสั้นและใช้คำแปลเดียวกันเมื่อเจอคำต้นฉบับเดียวกัน
- **ถามผู้ซื้อ:** ใช้ listing เพื่อดูว่าประเด็นไหนเกี่ยวข้อง และใช้ buyer context เพื่อดูว่าผู้ซื้อตั้งใจใช้อย่างไร ให้น้ำหนักกับคำถามเรื่องการใช้งานที่ยังไม่ชัดเมื่อคำตอบเปลี่ยนสิ่งที่ต้องตรวจ เช่น การสัมผัสอาหารโดยตรง แต่เรียงตามผลต่อกรณีซื้อจริง ไม่ดันเรื่องความปลอดภัยหรือข้อกำหนดขึ้นก่อนเสมอ ถ้าผู้ซื้อบอกการใช้งานชัดแล้วให้ใช้ข้อมูลนั้น ไม่ถามซ้ำหรือให้ผู้ซื้อเดาข้อเท็จจริงสินค้า ถามเฉพาะข้อที่เป็นอิสระกันในรอบเดียว สูงสุด 5 ข้อ และเลือกจากคำตอบสะสมในรอบถัดไป

ให้ C ใช้เกณฑ์ V01-C และ V02-C ตรวจผลจริงกับ raw ZIP และ T1/T2 ชุดเดิม ตัวอย่างและคำตอบที่คาดหวังใน verification ใช้ฝั่งทดสอบเท่านั้น

## งบภาพและหลักฐาน

ขั้นแปลและขั้นคำถามใช้ข้อความอย่างเดียว รุ่นแรกให้ขั้นรายงานส่งเฉพาะภาพที่ผูกกับตัวเลือกที่ยืนยัน สูงสุด 3 รูปต่อกรณีซื้อ ไม่อ้างว่าตรวจรูปครบทั้งหน้า

1. ส่งภาพที่ผูกกับตัวเลือกที่ยืนยันก่อน สูงสุด 3 รูป ถ้ามีและอ่านไฟล์ได้
2. ไม่ส่งรูป SKU ที่ไม่ได้เลือกมาเป็นหลักฐานของตัวเลือกที่เลือก ไม่เพิ่มงานคัดแยกรูปรายละเอียดจากโฆษณา/ไอคอนใน importer รุ่นแรก รายงานต้องมี limitation ว่า “Product-detail images were not reviewed in this version.”
3. ไม่ส่งไฟล์เดียวกันซ้ำเพียงเพราะอ้างหลายตำแหน่ง ผูก source IDs กลับให้ถูก ภาพหายหรืออ่านไม่ได้ให้แจ้งตามสถานะจริง ไม่ยืมภาพของอีก SKU
4. ใน input ของขั้นรายงานให้มี inventory ข้อความของภาพที่ snapshot รู้จัก พร้อม source_id, label, option_ids, availability และแยกรายการ IDs ที่แนบภาพจริงกับที่ไม่ได้แนบอย่างชัดเจน การส่ง metadata ไม่เท่ากับการอ่านภาพ บันทึกชุดที่ส่งจริงใน coordinator ฝั่ง Backend และปฏิเสธ image citation นอกชุดนั้น ภาพที่ไม่ได้ส่งคงเป็น not_reviewed ไม่เปลี่ยน availability เพื่อแกล้งว่าไฟล์อ่านไม่ได้ ไม่มีการเพิ่ม field ให้ Source contract เพื่อทำข้อนี้
5. ไม่ตัดข้อความที่มีผลต่อ SKU หรือข้อกล่าวอ้างเงียบ ๆ หากข้อมูลเกินงบที่วัดได้ให้แจ้งว่าไม่สามารถตรวจชุดนี้ได้ครบ ไม่อ้างว่าอ่านทั้งหน้า

ใช้ `detail: auto` เป็นจุดเริ่มต้นในการลอง API ทั้งสองรุ่น ถ้าจำเป็นให้เทียบกับ high/original ที่รุ่นนั้นรองรับ ไม่ถือว่าเพิ่ม detail แล้วสร้างรายละเอียดที่ไฟล์เดิมไม่มี ภาพตัวเลือกจริง 150×150 อ่านเฉพาะข้อความที่ชัดเป็น image observation หากไม่ชัดให้ unknown ห้ามสรุปวิธีผลิตลาย ความทน หรือความจุที่วัดได้จากภาพ ข้อจำกัด small text และการย่อภาพอธิบายใน [Images and vision](https://developers.openai.com/api/docs/guides/images-vision)

หากจะเพิ่มภาพรายละเอียดภายหลัง ต้องกำหนดส่วนที่อ่าน การแยกภาพที่ไม่เกี่ยวข้อง และการผูก scope ใน intake-contract ก่อน รวมถึงทบทวนเวลาและขอบเขตงาน ไม่ถือว่าอ่านครบเพียงเพราะมี source inventory และไม่เพิ่มรอบถามผู้ซื้อเพื่อให้เดาเนื้อหาภาพที่ยังไม่ตรวจ

## กฎจัดลำดับที่ต้องใส่ใน prompt

ใช้กฎทั่วไปจากพฤติกรรมรายงานที่ยอมรับแล้ว โดยไม่ส่งเฉลยของสินค้าตัวอย่างให้โมเดล:

- หากมี requirement ชัด ให้เรื่องที่ยังไม่ยืนยันว่าตรง requirement นั้นอยู่ก่อน พร้อมเหตุผลจากกรณีซื้อ
- แยกการตัดสินใจของผู้ซื้อ ข้อเท็จจริงที่ต้องถามผู้ขาย และหลักฐานที่ต้องขอ หากมี preference ที่ยังไม่ทราบให้รักษา open preference ไม่เปลี่ยนให้เป็น requirement หรือให้ผู้ขายตัดสินใจแทน
- จัดลำดับตามผลต่อกรณีซื้อและอธิบายเหตุผล ไม่บังคับชนิดประเด็นใดเป็นอันดับแรกเสมอ ไม่ให้ Backend ย้ายลำดับด้วยชื่อ finding หรือ hardcode คำตอบของสินค้าตัวอย่าง
- เมื่อผู้ซื้อเปลี่ยนหรือผ่อนเงื่อนไข ให้ใช้ความต้องการล่าสุดใน scope เดียวกัน ปรับเหตุผลและลำดับ ไม่คง requirement ที่ผู้ซื้อไม่ได้กำหนด

กฎทั่วไปนี้ยังต้องตรวจด้วย API จริง ไม่ใช้ตัวอย่างเฉลยหรือกฎเฉพาะเคสพิสูจน์การค้นพบ/จัดลำดับด้วยตัวเอง

## รูปแบบคำตอบและการรับมือเมื่อไม่ได้ผล

ให้ Python เป็นเจ้าของ schema ที่ใช้กับ structured outputs และ validation ฝั่ง Backend ไม่ให้ frontend แก้ JSON หรือตีความผลใหม่ Schema ครอบคลุมรูปข้อมูล ส่วนกฎ ID, scope, quote, requirement และความหมายต้องตรวจเพิ่ม unknowns ที่อ้าง source ของ SKU เฉพาะต้องเกี่ยวกับตัวเลือกของ finding นั้นด้วย ไม่ตรวจเพียงว่า ID มีอยู่ Structured outputs ยังให้เนื้อหาผิดได้ตาม [เอกสาร OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs)

เสนอ `max_output_tokens` เริ่มต้น 4,096 สำหรับแปล, 4,096 สำหรับคำถาม และ 12,288 สำหรับรายงาน ทั้งหมดรวม reasoning tokens ไม่ใช่เพดานข้อความที่ผู้ใช้เห็น ต้องปรับจาก usage/ผล incomplete จริง ไม่ตัด JSON แล้วแสดงต่อ หาก output ไม่ครบหรือเกิด refusal ให้ failed ตามขั้นนั้น ข้อมูล reasoning ถูกคิดราคาเป็น output ตาม [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)

| ปัญหา | พฤติกรรมที่เสนอ |
| --- | --- |
| Client input หรือ plan/case ID ไม่ถูก | ปฏิเสธก่อนเรียก AI ไม่ลองให้โมเดลซ่อมข้อมูลผู้ซื้อ |
| 401/403, model หรือ schema config ไม่รองรับ, เครดิต/โควตาหมด | หยุดและแจ้งปัญหาตั้งค่า ไม่ retry ซ้ำหรือสลับเป็น sample |
| Rate limit ชั่วคราวหรือ 5xx | retry อัตโนมัติได้อีกครั้งตาม Retry-After ภายใน timeout ที่ตั้งไว้ |
| JSON/รหัส/quote ไม่ผ่านตรวจ | ส่งข้อผิดพลาดที่ตรวจได้ให้แก้ได้อีกครั้ง โดยใช้ input เดิม ไม่เติมความต้องการหรือหลักฐานใหม่ |
| Timeout, refusal หรือ output ไม่ครบ | แสดงผลล้มเหลวและให้ลองใหม่โดยรักษาข้อมูลผู้ใช้ ไม่เพิ่มรอบคำถาม |
| แปล timeout/output/validation หรือ rate limit ชั่วคราว/5xx ที่ retry ครบหรือ deadline หมดแล้ว | คืน null พร้อม limitation ตาม intake-contract ใช้ชื่อเดิม ไม่แต่งคำแปลหรือใช้ sample ข้อผิดพลาดตั้งค่า/สิทธิ์/โควตาตามแถวบนหยุด import เป็น intake_failed ไม่ลดเป็น ready |

เพดานรวมคือไม่เกิน 2 attempts ต่อการรันแต่ละขั้น รวมทั้ง transport retry และการแก้ผล ไม่ให้ SDK retry ซ้อนจนเกินเพดาน กำหนด deadline ต่อขั้น 60 วินาทีสำหรับแปล, 60 วินาทีสำหรับคำถาม และ 90 วินาทีสำหรับรายงาน นับรวมทุก attempt, backoff และการตรวจผล ไม่ใช่ timeout ใหม่เต็มจำนวนทุกครั้ง ใช้เวลาที่เหลือเป็น timeout ของ request ถัดไป หาก Retry-After เกินเวลาที่เหลือให้หยุด ไม่รอจนเกิน deadline

เมื่อถึง deadline ให้จบขั้นนั้นเป็นผลล้มเหลว หรือ null/limitation สำหรับคำแปลตาม contract ไม่รับผลที่มาช้ากลับมาเป็นผลปัจจุบัน เพดานรอรวมของ 1 แปล + 3 รอบถาม + 1 รายงานประมาณ 330 วินาทีบวก overhead เมื่อทุกขั้นใช้เวลาเต็ม โดยไม่รวมเวลาที่ผู้ซื้ออ่าน/ตอบ ไม่ใช่ latency เป้าหมาย ผู้ซื้อเลือกลองใหม่ได้โดยรักษาข้อมูลเดิมและไม่ต้องตอบคำถามใหม่ ต้องวัดจริงกับเน็ตและบัญชีที่จะใช้

เมื่อผู้ใช้กด Retry หลัง failed ให้เริ่ม stage run ใหม่ด้วย case_id/revision/operation_id และ input ที่บันทึกไว้เดิม มี deadline และเพดาน 2 attempts ของ run ใหม่นั้น ไม่ใช่โควตา 2 attempts ตลอดอายุ case ส่วนการส่งซ้ำขณะ running ไม่เปิด run ซ้อน และ ready ที่ข้อมูลเดิมใช้ผลเดิมตาม [แผนเชื่อมระบบ](integration-plan.md#case-ids-retry-และผลเก่า) ใช้ AsyncOpenAI โดยปิด SDK retries เพื่อไม่ให้นับซ้อน

ตรวจ error code แยก quota ออกจาก rate limit ตาม [Error codes](https://developers.openai.com/api/docs/guides/error-codes) ขั้นที่ผิดข้อมูลสินค้าเชิงความหมายอาจผ่าน schema/quote ได้ จึงต้องมีการอ่านผลเทียบหลักฐานจริงในการทดสอบ ไม่อ้างว่า validator จับ hallucination ได้ทั้งหมด

## ประเมินงบ $100

ตัวอย่างคำนวณเพื่อวางงบ: ทั้งเส้นทางรวม 30,000 billed input tokens และ 20,000 billed output tokens ค่าภาพคิดเป็น input ตามโมเดล และ reasoning รวมใน output แล้ว ตัวเลข output นี้ใช้เป็นตัวอย่างวางงบสำหรับเส้นทางสั้น ถ้าถามครบสามรอบ input/output อาจเพิ่มเพราะส่งหลักฐานและคำตอบสะสมอีก ไม่ใช่การคาดว่าแต่ละรอบใช้เต็มเพดานหรือเป็นขีดจำกัดต้นทุนรวม ตัวเลขทั้งหมดเป็นสมมติฐาน ไม่ใช่ผลนับ tokens ของ ZIP หรือรายงานจริง

## วิธีเลือกก่อนใช้จริง

แยกคำสั่ง deterministic ที่ใช้ stub/fixture และไม่เรียก API ออกจากคำสั่ง live ที่ใช้เครดิต บันทึก app cache mode และว่า hit หรือไม่ในหลักฐานของ live run ปิด app cache สำหรับการตรวจความหมาย การวัด latency/usage และ T1–T5 ของ PR-04 เพื่อให้วัดจากการเรียกโมเดลจริง กฎ HTTP สำหรับผลเดิมของ case เดิมยังใช้ตาม integration plan

SQLite เก็บเคสล่าสุดเพื่อ resume ไม่ใช้เป็น cache ข้ามเคส ค่าเริ่มต้นไม่เปิด disk cache เพิ่ม หากทีมเลือกเพิ่มภายหลังเพื่อรัน UI ซ้ำ ให้ระบุสิ่งที่เขียนลงดิสก์ (รวมข้อความที่อาจถอดความจาก buyer context) อายุข้อมูล วิธีปิดและลบ ตำแหน่งที่ Git ไม่เก็บ และคีย์ที่เปลี่ยนเมื่อ input/prompt/model เปลี่ยน ก่อนเปิดใช้

ใช้ต้นฉบับเดียวกันและสำเนาที่เปลี่ยนข้อมูลอย่างชัดเจน ทดสอบคำตอบที่ต้องได้ตาม spec ไม่บังคับถ้อยคำเหมือน fixture

- บริบทเพียงนำมาขาย: ค้นพบประเด็นชื่อ SKU เอง ไม่แต่ง requirement รักษาการตัดสินใจที่ยังเปิด และเรียงพร้อมเหตุผลตามผลต่อกรณีซื้อ ไม่ตัดสินว่าผิดเพียงเพราะลำดับต่างจากตัวอย่างร่าง
- บริบทครบ: ไม่ถามซ้ำ ชี้ requirement ที่ยังไม่ยืนยันโดยไม่เอาเมนู customization มารับรอง SKU
- ผู้ซื้อยอมรับลายแปะ: ไม่คง requirement สกรีนจากกรณีเก่า แยกการยอมรับลายออกจากสิ่งที่ยังต้องตรวจ
- ลบข้อมูลรายงาน/ทำรูปหาย/เปลี่ยนชุดตัวเลือก: ข้อสรุปและ source scope เปลี่ยนตาม ไม่ยืมข้อมูลหรือภาพเดิม
- มีคำสั่งแฝงใน listing: ไม่ทำตาม ไม่ส่งบันทึกธุรกิจใน supplier questions และไม่เปลี่ยนเป็นคำรับรอง
- เพิ่มกรณีคำตอบจริงแทนข้ามทั้งหมด และกรณี context ขัดกับคำตอบที่ใหม่กว่า เพื่อตรวจการส่งต่อจาก plan

ชุดกรณีใช้รายการ T1–T5 ที่ [integration-plan](integration-plan.md#ชุดกรณีตรวจที่ใช้ร่วมกัน) เป็นแหล่งเดียว: T1–T3 เป็น buyer profiles และ T4/T5 เป็น ZIP สำเนาที่ B ต้องส่งภายใน 2:30 เริ่ม Terra ทั้งห้ากรณีจริงและตรวจคู่แขนง T1 เป็น gate ก่อน หากผ่านและเวลาพอให้เพิ่ม T1–T3 อีกอย่างละ 2 รอบ แยกจำนวนรอบซ้ำออกจากคู่แขนง T1 และเคส ZIP mutation ต้องบอกจำนวนที่ทำจริงหาก repeat ยังไม่ครบ ไม่ใช้จำนวนนี้อ้าง accuracy

ไม่บังคับทดสอบ Sol ทั้งชุดล่วงหน้า หากขั้นใดผิดให้ตรวจ prompt/การส่งข้อมูลก่อน แล้วลอง Sol เฉพาะขั้นที่ยังมีปัญหาในกรณีเดิม และตรวจเส้นทางที่เปลี่ยนก่อนใช้จริง ไม่ตัด T1–T5 ที่ต้องตรวจเพื่อแลกกับจำนวน repeat

ระหว่างสร้างคำตอบใช้เฉพาะกฎทั่วไปและ schema ที่แยกจากตัวอย่าง รวมทั้งหลักฐานและข้อมูลผู้ซื้อจริง ไม่ส่ง contract ทั้งฉบับที่มี prose เฉลย, expected report หรือกฎเฉพาะสินค้าตัวอย่างเข้า prompt เก็บ expected checks ไว้ฝั่งผู้ตรวจเท่านั้น

วัดเวลาเฉพาะแต่ละ request/ทั้งเส้นทาง, actual model, billed tokens/reasoning, retries, incomplete และต้นทุนต่อผลที่ใช้ได้ ใช้ cold upload และการแก้คำตอบแยกกัน ไม่คิดเวลาผู้ใช้อ่าน/ตอบเป็น latency โมเดล

ตั้งเป้าเริ่มต้นให้แปลก่อนเลือกสินค้าไม่เกิน 15 วินาที แต่ละรอบคำถามไม่เกิน 15 วินาที และรายงานไม่เกิน 45 วินาทีในรอบส่วนใหญ่ เป้าหมายนี้ยังไม่ใช่ผลวัดหรือ SLA หากไม่ผ่านให้ลองลด effort สำหรับงานแปล/งานที่ง่ายหรือลดเนื้อหาซ้ำโดยคงหลักฐาน แล้วตรวจคุณภาพใหม่ ไม่ลดข้อกำหนดให้ผ่านตัวเลข

เลือก Terra ต่อเมื่อผ่านข้อห้ามสำคัญและผลมีประโยชน์ หากผลผิดชัดเจนให้แก้ prompt/การส่งข้อมูลก่อน หากยังไม่ผ่านจึงใช้ Sol ในงานที่มีปัญหา พร้อมลองเส้นทางใหม่จริง ไม่ใช้คะแนนรวมกลบข้อผิดพลาดที่มีผลต่อผู้ซื้อ
