# Spec: ตรวจความเสี่ยงเบื้องต้นก่อนสั่งซื้อสินค้าเพื่อนำมาขาย

Status: accepted design; no Build or deployment authorization
Version: 0.16
วันที่: 20 พ.ย. 2569
ต้นทาง: [intent ที่ยอมรับแล้ว](brief.md), [ผลค้นแหล่งอ้างอิง](reference-pack.md), [คำศัพท์](GLOSSARY.md)

ยอมรับ spec v0.15 เป็น baseline วันที่ 19 พ.ย. 2569 ตามคำตอบ “ไปต่อขั้นต่อไปเลย” หลังรีวิวและแก้ข้อค้นพบแล้ว ฉบับ v0.16 เพิ่มคำถามหลายรอบและการกู้เคส SQLite ตามข้อตกลงล่าสุด ดู [บันทึกการยอมรับและขอบเขต](acceptance.md) ใช้เป็น baseline สำหรับแตกงาน ไม่เป็นคำสั่ง Build หรือ deploy ค่าเวลา/ต้นทุนเป็นสมมติฐานที่ต้องวัด ส่วนโมเดลเริ่มต้นต้องผ่านการตรวจ API ของบัญชีตามแผน

## Problem Statement

ผู้ซื้อสินค้าเพื่อนำมาขายอาจไม่เข้าใจว่าข้อความในตัวเลือกมีผลต่อสิ่งที่จะได้รับ และไม่รู้ว่าต้องตรวจประเด็นใดเพิ่ม ในเคสจริง ผู้ซื้อเข้าใจจากภาพว่าลายกระติกเป็นงานสกรีน แต่ได้รับลายแบบสติกเกอร์ แล้วจึงย้อนพบคำจีนในตัวเลือกสินค้า

ข้อมูลจากหน้าสินค้ากระจัดกระจายระหว่างภาพ ตัวเลือก และคุณสมบัติทั่วไป การอ่านข้อมูลออกหรือแปลได้ยังไม่เพียงพอ ระบบต้องเชื่อมข้อมูลให้ถูกกับสิ่งที่จะซื้อและสิ่งที่ผู้ซื้อต้องการ โดยไม่อ้างความมั่นใจเกินหลักฐาน

## Solution

รับลิงก์หน้าสินค้า TTP Cargo สำหรับ provider 1688, Taobao หรือ Tmall เป็นช่องทางหลัก หรือรับ ZIP ของหน้าที่ผู้ใช้บันทึกไว้ตาม [intake contract](contracts/intake-contract.md) อ่าน HTML และรูปประกอบ แสดงตัวเลือกให้ยืนยัน 1–3 ตัวเลือกจากหน้าเดียวกัน และรับบริบทการซื้อซึ่งผู้ใช้บอกมากหรือน้อยได้ ใช้หนึ่งรายงานต่อกรณีซื้อ ประเด็นร่วมแสดงครั้งเดียวและประเด็นเฉพาะผูกกับตัวเลือกที่เกี่ยวข้อง

ระบบอ่านหลักฐานและบริบทก่อน ถ้าจำเป็นจึงถามผู้ซื้อสูงสุด 3 รอบ รอบละไม่เกิน 5 ข้อสำหรับทั้งกรณีซื้อ ถามข้อที่เป็นอิสระต่อกันพร้อมกันและปรับรอบถัดไปตามคำตอบ ผู้ซื้อข้าม ตอบไม่ทราบ หรือจบคำถามก่อนก็ได้ ทุกเส้นทางให้ตรวจและยืนยัน buying brief ก่อนสร้างรายงาน รวมถึงกรณีที่ไม่มีคำถาม

Buying brief แสดงข้อกำหนดตาม SKU พร้อมข้อความที่ผู้ซื้อให้จริงและประเด็นที่ยังเปิดอยู่ ผู้ซื้อแก้หรือ Undo เพื่อดูผลก่อนบันทึกได้ เงื่อนไขสั่งทำที่อ้างถึงวันของถึงจะเปลี่ยนตามวันของถึงของ SKU นั้นเมื่อความหมายชัดเจน รายงานใช้เฉพาะ revision ที่ผู้ซื้อยืนยันแล้ว

ผลสุดท้ายเป็นรายงานเรียงประเด็นตามความสำคัญ มีหลักฐาน เหตุผล สิ่งที่ยังไม่ทราบ และสิ่งที่ควรตรวจต่อ โดยแสดงครบ 3 กลุ่ม:

1. สินค้าและตัวเลือกตรงความต้องการหรือไม่
2. การใช้งานทำให้ต้องตรวจเรื่องใดเพิ่ม
3. ข้อมูลรองรับรุ่นที่จะซื้อเพียงพอหรือไม่

รายงานแสดงทั้งข้อค้นพบและเรื่องที่ยังประเมินไม่ได้ กลุ่มทั้งสามสัมพันธ์กันได้ และไม่จำเป็นต้องพบปัญหาทุกกลุ่ม ใช้ชุดเอกสารทางการที่คัดไว้ประกอบการตรวจ ไม่ค้นเว็บอิสระสดในรุ่นหลัก

## User Stories

1. ในฐานะผู้ซื้อ ต้องการส่ง ZIP ของหน้าสินค้าที่เซฟไว้ เพื่อให้ตรวจข้อมูลได้โดยไม่พึ่งการเปิดเว็บต้นทางสด
2. ในฐานะผู้ซื้อ ต้องการเห็นและยืนยัน 1–3 ตัวเลือกที่จะซื้อจากหน้าเดียวกัน เพื่อไม่ให้ระบบตรวจผิดรุ่นหรือใช้ค่าเริ่มต้นของเว็บแทนการตัดสินใจ
3. ในฐานะผู้ซื้อ ต้องการบอกวัตถุประสงค์และข้อกำหนดได้ตามที่ทราบ เพื่อให้คำแนะนำตรงกับบริบทจริง
4. ในฐานะผู้ซื้อที่ยังไม่รู้ว่าต้องระวังอะไร ต้องการให้ระบบค้นพบประเด็นที่ควรตรวจจากหลักฐาน โดยไม่ต้องถามประเด็นนั้นล่วงหน้า
5. ในฐานะผู้ซื้อ ต้องการให้คำตอบที่ส่งแล้วเปลี่ยนสิ่งที่ระบบถามต่อและสิ่งที่รายงานแนะนำ เพื่อใช้เวลาตอบเฉพาะเรื่องที่มีผล
6. ในฐานะผู้ซื้อ ต้องการข้ามคำถามหรือตอบไม่ทราบได้ เพื่อรับรายงานโดยไม่ถูกบังคับให้เดาคำตอบ
7. ในฐานะผู้ซื้อ ต้องการเห็นข้อค้นพบที่ผูกกับตัวเลือกที่ยืนยัน เพื่อไม่เอาคุณสมบัติของอีกตัวเลือกมาปน
8. ในฐานะผู้ซื้อ ต้องการเปิดข้อความหรือรูปต้นทางของข้อค้นพบ เพื่อประเมินว่าข้อสรุปมีหลักฐานรองรับจริงหรือไม่
9. ในฐานะผู้ซื้อ ต้องการแยกข้อมูลที่ผู้ขายระบุออกจากสิ่งที่ระบบอนุมาน เพื่อไม่เข้าใจคำกล่าวอ้างเป็นผลพิสูจน์
10. ในฐานะผู้ซื้อ ต้องการเห็นเรื่องที่ยังตรวจไม่ได้และเหตุผล เพื่อไม่เข้าใจว่าไม่มีคำเตือนแปลว่าตรวจผ่านแล้ว
11. ในฐานะผู้ซื้อ ต้องการรู้ว่าประเด็นใดควรจัดการก่อนและควรถามอะไรต่อ เพื่อใช้รายงานก่อนตัดสินใจสั่งซื้อ
12. ในฐานะผู้ซื้อ ต้องการเห็นว่าเอกสารทางการเกี่ยวข้องกับประเด็นใดและยังขาดเงื่อนไขอะไร เพื่อไม่สรุปว่าข้อกำหนดบังคับใช้โดยไม่มีข้อมูลพอ
13. ในฐานะผู้ซื้อ ต้องการใช้ข้อมูลส่วนที่อ่านได้แม้ไฟล์ไม่ครบ โดยเห็นข้อจำกัด เพื่อไม่เสียงานตรวจทั้งหมด
14. ในฐานะผู้ซื้อ ต้องการได้รับแจ้งเมื่อไฟล์อ่านไม่ได้ ตัวเลือกยังไม่ยืนยัน หรือบริการวิเคราะห์ล้มเหลว เพื่อไม่รับรายงานที่ตรวจผิดหรือไม่สมบูรณ์โดยไม่รู้ตัว
15. ในฐานะทีมเดโม ต้องการตรวจผลจากโจทย์จริงและกรณีที่เปลี่ยนข้อมูล เพื่อพิสูจน์ว่าระบบตอบตามหลักฐานและความต้องการ ไม่ใช่เพียงสร้างคำตอบได้

16. ในฐานะผู้ซื้อ ต้องการเปิดเคสล่าสุดหลังแอป restart แล้วเห็น SKU รูปและคำตอบที่ส่งแล้ว เพื่อทำต่อได้จากจุดเดิม

## Implementation Decisions

### พฤติกรรมที่ตกลงแล้ว

- รองรับ ZIP ของเว็บ TTP Cargo ตามโครงสร้างตัวอย่างก่อน อ่านข้อมูลจริง ไม่ผูกคำตอบกับ item ID ของเคสเดโม และไม่อ้างว่ารองรับทุกเว็บ
- ถ้าอ่านข้อมูลสินค้าไม่ได้หรือยังไม่ยืนยันตัวเลือก ให้หยุดก่อนตรวจ หากขาดข้อมูลเพียงบางส่วนแต่ยังตรวจได้ ให้ออกรายงานพร้อมข้อจำกัด
- รับบริบทเริ่มต้นโดยไม่บังคับให้ผู้ซื้อรู้ประเด็นความเสี่ยงล่วงหน้า ไม่สมมติการใช้งานหรือข้อกำหนดที่ผู้ซื้อไม่ได้ให้
- แสดงคำถามทั้งรอบและส่งพร้อมกัน สูงสุด 3 รอบ รอบละ 5 ข้อ ถ้าส่งเพื่อดูรายงานทันทีให้ใช้คำตอบที่กรอกไว้ด้วย ข้อที่ข้ามเป็น unknown
- ข้อมูลความต้องการถามผู้ซื้อได้ ส่วนข้อเท็จจริงสินค้าใช้หลักฐานที่มี หากขาดให้ระบุสิ่งที่ต้องขอจากผู้ขาย ไม่ใช้ข้อมูลสินค้าหน้าตาเหมือนจากที่อื่นแทน
- แยกข้อความในเอกสารทางการออกจากข้ออนุมานว่าบังคับใช้กับสินค้า เมื่อเงื่อนไขไม่ครบให้บอกสิ่งที่ต้องตรวจเพิ่ม ไม่ฟันธงจากคำวัสดุอย่างเดียว
- ไม่ใช้ภาพเพียงอย่างเดียวฟันธงเทคนิคตกแต่ง ไม่ใช้รายการวิธีปรับแต่งทั่วไปยืนยันคุณสมบัติตัวเลือก และไม่ใช้การไม่มีรายงานทดสอบยืนยันว่าสินค้าไม่ปลอดภัย
- เน้นเดโม local ที่เชื่อมอินเทอร์เน็ตสำหรับ OpenAI API ทีมถนัด Python เป็นหลัก มีเครดิต OpenAI $100 ตามที่ผู้ใช้แจ้ง
- ผู้ใช้เลือก TypeScript สำหรับ frontend แล้ว Python เป็นข้อเสนอสำหรับ backend ที่อ่าน ZIP และวิเคราะห์ การเลือก framework และการเชื่อมงานยังเป็นรายละเอียด Design
- เรียงประเด็นตามผลต่อการตัดสินใจซื้อครั้งนี้และอธิบายเหตุผล แยกความสำคัญออกจากความแน่นอนของหลักฐาน ไม่ใช้คะแนนเดียวแทนสองมิตินี้
- หลังลอง mock ผู้ใช้กำหนดให้ UI ใช้ภาษาอังกฤษเป็นหลัก คงบริบทนำเข้าไทยและหลักฐานจีนต้นฉบับ ไม่เปลี่ยนประเทศที่ใช้ตรวจตามภาษา UI
- แปลเนื้อหาที่มีผลต่อการเลือกและตัดสินใจให้ตรงบริบท เช่น ชื่อตัวเลือก วัสดุ วิธีปรับแต่ง และหลักฐานที่แสดง ต้องไม่แปลรายการวิธีที่ร้านรองรับให้เป็นคุณสมบัติยืนยันของตัวเลือก
- รูปต้องเปลี่ยนตามตัวเลือกโดยใช้ mapping จากต้นทาง หากไม่มีรูปเฉพาะให้แจ้งว่าเป็นภาพสินค้ารวม ไม่แสดงภาพของอีกตัวเลือกโดยไม่บอก

### Purchase review refinement ที่ยอมรับแล้ว

ผู้ใช้ยอมรับแนวทางทั้ง 6 ข้อและให้ปรับ mock วันที่ 17 พ.ย. 2569 การยอมรับนี้ครอบคลุมพฤติกรรมรายงาน ไม่ใช่การยอมรับ spec ทางเทคนิคทั้งฉบับหรือเริ่ม Build

- สรุปแยกสิ่งที่ผู้ซื้อต้องตัดสินใจ ข้อเท็จจริงที่ต้องถามผู้ขาย และหลักฐานที่ต้องขอ พร้อมเหตุผลการเรียงลำดับตามกรณีซื้อ ไม่เปิดรอบถามในหน้าผลรายงาน
- วางข้อความต้นทางและคำแปลใกล้ข้อสรุป แยกคำอ้างผู้ขาย คำตอบผู้ซื้อ สิ่งที่พบ และสิ่งที่ยังไม่พบในส่วนที่อ่านได้ ไม่แสดง verified เพียงเพราะพบข้อความในไฟล์
- แสดง Before you order ก่อน แล้วเปิดตารางความต่างของตัวเลือกให้เห็นโดยไม่ต้องกดขยาย แสดงความจุจาก selector และภาพตามขอบเขตหลักฐาน ไม่ใช้การไม่พบคำเตือนจัดอันดับความปลอดภัย
- แต่ละประเด็นระบุข้อมูลหรือหลักฐานที่ช่วยประเมินต่อ และข้อจำกัดของสิ่งนั้น คำตอบผู้ขาย รูป และรายงานทดสอบไม่เท่ากับพิสูจน์คุณภาพสินค้าจริงทั้งหมด
- อธิบายเหตุที่ค้นพบประเด็นที่ผู้ซื้อไม่ได้ถาม เช่น ฝา PP ทำให้ต้องดูส่วนสัมผัสเครื่องดื่มนอกเหนือจากตัวกระติก แหล่งทางการช่วยตั้งคำถาม ไม่รับรองสินค้านี้
- ข้อความถึงผู้ขายเรียงตามประเด็นในรายงาน รักษาชื่อ SKU และใช้เฉพาะ requirement ที่เกี่ยวข้อง ไม่คัดลอก buyer context ทั้งก้อน ยังแก้ไขและคัดลอกได้โดยไม่มีการส่งจริง
- ลดข้อความซ้ำ คง coverage 3 กลุ่ม แต่ไม่บังคับจำนวนข้อค้นพบเป็น 3 และไม่ใช้คะแนนรวมความเสี่ยงหรือความมั่นใจแทนหลักฐาน

ดู [mock อ้างอิง](../references/mock-reference.html) สำหรับสไตล์รายงานและการเปิดหลักฐาน หน้าคำถามใน mock เป็นแบบก่อนเปลี่ยนเป็นหลายรอบและใช้ผลจำลอง

### Interface ที่ยอมรับเพื่อแบ่งงาน

ข้อตกลงต่อไปนี้ยอมรับสำหรับรุ่นแข่งแล้ว ไม่อ้างว่า implementation ผ่านการตรวจหรือเหมาะกับระบบหลายผู้ใช้

รายละเอียด Interface รายงานอยู่ใน [report-contract.md](contracts/report-contract.md) v0.9 พร้อม [JSON ตัวอย่าง](contracts/examples/report-contract-example.json) เอกสารนั้นเป็นแหล่งรายละเอียดเดียวของ fields และ invariants ที่ยอมรับในรุ่นนี้

รอบคำถามก่อนรายงานกำหนดใน [question contract](contracts/question-contract.md) v0.6 พร้อม [ตัวอย่างที่เชื่อมกับรายงาน](contracts/examples/question-contract-examples.json) แบบ 0–3 รอบ ใช้คำถามที่ออกจริงและคำตอบของ revision ปัจจุบัน ไม่ให้ Frontend ตีความคำตอบหรือให้โมเดลรายงานแต่งคำถามที่ไม่เคยถาม

การรับ archive กำหนดใน [intake-contract.md](contracts/intake-contract.md) v0.5 เป็นข้อเสนอจากการสำรวจ saved HTML/assets จริง รวมเพดานไฟล์ที่เสนอและเงื่อนไขหยุดเมื่อระบุ SKU ไม่ได้ ยังไม่ได้ทดสอบ importer จริง ส่วนข้อจำกัดโครงสร้าง SKU ได้รับการยอมรับในรุ่นนี้แล้ว

รายละเอียดการเรียก AI ที่เสนออยู่ใน [ai-execution-plan.md](ai-execution-plan.md) v0.6 แยกแปล 1 call คำถามสูงสุด 3 ขั้น และรายงาน 1 call ต่อเส้นทางปกติ คำถามใช้ข้อความ ส่วนรายงานรุ่นแรกเสนอเฉพาะภาพตัวเลือกสูงสุด 3 รูปพร้อมข้อจำกัดว่ารูปรายละเอียดยังไม่ตรวจ มีเพดาน attempts/deadline ต่อ stage run และงบสมมติ เป็น baseline ที่ยอมรับแต่ยังไม่ได้ยืนยันด้วย API ของแอป ไม่ใช้กฎลำดับเฉพาะเคสหรือ prose เฉลยเข้า prompt

การเชื่อม local frontend/backend, HTTP, SQLite สำหรับกู้เคส/ภาพ, case/revision/retry, การแบ่ง A/B/C และจุดตรวจ 6 ชั่วโมงอยู่ใน [integration-plan.md](integration-plan.md) v0.6 ใช้ React/TypeScript/Vite + FastAPI หนึ่ง process หนึ่งเคสปัจจุบันที่กู้หลัง restart ได้ ชุด T1–T5 ในแผนนั้นเป็นรายการเดียวที่ใช้ตรวจรวม ข้อมูลกรณีซื้อและ bytes ภาพอยู่ฝั่ง server ไม่รับ source/path จาก client เป็น baseline ที่ยอมรับสำหรับแบ่งงานแล้ว ส่วนคุณภาพ/เวลาและข้อจำกัดจริงยังต้องทดสอบ

| Module | รับข้อมูล | ส่งผล | ความรับผิดชอบ |
| --- | --- | --- | --- |
| รับหลักฐาน | ZIP | ข้อมูลสินค้า ตัวเลือก ข้อความ รูป และข้อจำกัดของไฟล์ พร้อมรหัสหลักฐาน | อ่านโดยไม่รันหน้าเว็บ รักษาที่มา แยกข้อมูลทั่วไปกับข้อมูลตัวเลือกเท่าที่ต้นทางรองรับ |
| ตรวจความเสี่ยง | ชุดหลักฐาน ตัวเลือกที่ยืนยัน บริบท และข้อความอ้างอิงที่คัดไว้ | คำถามที่มีเหตุผลรองรับ แล้วรายงานหลังตอบหรือข้าม | ค้นพบประเด็น ใช้คำตอบปรับผล แยกข้อมูลที่พบ ข้ออนุมาน และเรื่องที่ยังไม่ทราบ |
| แสดงรายงาน | รายงานและชุดหลักฐานเดียวกับที่ใช้ตรวจ | ข้อค้นพบครบ 3 กลุ่ม พร้อมเปิดหลักฐานและขั้นตอนต่อไป | แสดงผลโดยไม่เพิ่มข้อกล่าวอ้างเอง และแสดงข้อจำกัด/ข้อผิดพลาดให้เห็น |

รหัสหลักฐานต้องอ้างถึงข้อความ รูป หรือเอกสารที่ระบบมีอยู่จริง ผลรายงานต้องระบุหลักฐานประกอบข้อกล่าวอ้างเกี่ยวกับสินค้า และแยกคำตอบจากผู้ซื้อออกจากข้อมูลผู้ขาย ข้อมูลที่ไม่ได้ให้หรือไม่ได้พบต้องคงเป็นไม่ทราบ

คำถามต้องมีเหตุผลว่าคำตอบจะเปลี่ยนประเด็นตรวจหรือคำแนะนำอย่างไร รายงานต้องมีข้อค้นพบ เหตุผล หลักฐาน ข้อมูลที่ขาด และขั้นตอนต่อไปที่ผู้ซื้อทำได้ การมีรหัสอ้างอิงถูกต้องยังไม่พิสูจน์ว่าข้อสรุปตรงกับความหมายของหลักฐาน

ต้องไม่รัน script/HTML จาก archive หรือถือข้อความในสินค้าเป็นคำสั่งระบบ การอ่าน ZIP ต้องตรวจเส้นทางไฟล์และจำกัดทรัพยากร รายละเอียดเพดานขนาดอยู่ใน intake-contract และงบรูปอยู่ใน ai-execution-plan

## Testing Decisions

### Seam และหลักตัดสินที่ผู้ใช้ยอมรับแล้ว

ทดสอบผ่านเส้นทางการใช้งานหลัก ตั้งแต่ ZIP พร้อมตัวเลือกและบริบท ไปยังคำถาม คำตอบหรือการข้าม และรายงานพร้อมหลักฐาน เกณฑ์หลักคือคำตอบตรงหลักฐานและความต้องการ การอ่าน ZIP สำเร็จ API สำเร็จ หรือ JSON ถูกต้องเป็นเพียงการตรวจระหว่างทาง

ประเมินความหมายที่ต้องได้และข้อกล่าวอ้างที่ห้ามเกิด ไม่บังคับถ้อยคำเดียวกับคำตอบตัวอย่าง ไม่ใช้ข้อความอ้างอิงที่เป็นคำตอบสำเร็จรูปแทนการอ่านหลักฐานจริง

### กรณีตรวจผล

| กรณี | สิ่งที่ต้องได้ | คำตอบผิดที่ต้องตรวจจับ |
| --- | --- | --- |
| เคสจริงกับโจทย์เพียงว่านำมาขาย | ค้นพบคำเกี่ยวกับภาพแปะและเหตุที่ควรยืนยัน เปิดหลักฐานตรงตัวเลือกได้ | ต้องใบ้เรื่องสติกเกอร์ก่อนจึงพบ หรือแต่งว่าผู้ซื้อกำหนดว่าต้องเป็นสกรีน |
| ผู้ซื้อยอมรับลายแปะ | คงข้อเท็จจริง แต่ไม่อ้างว่าขัดความต้องการเรื่องงานสกรีน ประเด็นวัสดุและหลักฐานยังพิจารณาต่อ | ยังกล่าวว่าตรงข้ามข้อกำหนดของผู้ซื้อ หรือสรุปว่ายอมรับลายแล้วทุกเรื่องผ่าน |
| ผู้ซื้อกำหนดว่าต้องเป็นสกรีน | ชี้ว่ายังไม่มีหลักฐานยืนยันว่าตัวเลือกนี้ตรงข้อกำหนด และเสนอให้ยืนยันก่อนสั่ง | เห็นรายการวิธีปรับแต่งทั่วไปมีสกรีนแล้วสรุปว่าตัวเลือกตรงข้อกำหนด |
| ข้ามคำถาม | รายงานครบ 3 กลุ่ม คงสิ่งที่ไม่ทราบพร้อมสิ่งที่ต้องตรวจต่อ | แต่งคำตอบหรือบังคับตอบจึงจะเห็นรายงาน |
| เปลี่ยนตัวเลือก | ผลยึดหลักฐานของตัวเลือกใหม่และข้อมูลทั่วไปที่เกี่ยวข้อง ตรวจด้วย T3 ที่เปลี่ยนทั้งชุดและลำดับตาม integration-plan | ย้ายข้อความของตัวเลือกเดิมมาใช้โดยไม่มีหลักฐาน |
| เอาข้อมูลรายงานทดสอบออกจากสำเนา | ระบุว่าไม่พบข้อมูลในหลักฐานที่มี | อ้างว่าผู้ขายระบุว่าไม่มีรายงานทั้งที่ข้อความนั้นไม่มีแล้ว |
| รูปประกอบหาย | ใช้หลักฐานที่เหลือและแจ้งสิ่งที่ตรวจไม่ได้ | อ้างว่าได้ตรวจรูปที่ไม่มี หรือแสดงว่าตรวจครบ |
| อ่านสินค้าไม่ได้หรือไม่ยืนยันตัวเลือก | หยุดพร้อมเหตุผลและสิ่งที่ต้องแก้ | สร้างรายงานของรุ่นที่เดาเอง |

| API ล้มเหลวหรือผลไม่สมบูรณ์ | แจ้งว่ายังไม่ได้ผลวิเคราะห์ที่ใช้ได้ | แสดงผลไม่ครบเป็นผลสำเร็จ หรือใช้ผลเก่าโดยไม่บอก |

กรณีเปลี่ยนข้อมูลต้องใช้สำเนาหลักฐานสำหรับตรวจ โดยไม่แก้ไฟล์ต้นฉบับให้กลายเป็นเรื่องจริงอีกแบบหนึ่ง การตรวจรุ่นจริงต้องเรียกโมเดลจริงและอ่านข้อสรุปเทียบหลักฐาน ไม่ใช้เฉพาะผลจำลองเพื่อประกาศคุณภาพโมเดล

ให้ตรวจความถูกต้องของรหัสหลักฐานและข้อมูลที่ส่งระหว่าง Module เพิ่มในจุดที่เป็นสาเหตุให้รายงานผิดได้ แต่ไม่ใช้สิ่งเหล่านี้แทนการตรวจผลปลายทาง ขณะนี้ยังไม่มีโค้ดหรือชุดทดสอบเดิมให้ใช้เป็น prior art

### สถานะหลักฐานการตรวจ

ชุดนี้มีเอกสารที่ยอมรับแล้ว ข้อมูลสินค้าจริงที่ตัดส่วนไม่จำเป็น และ mock อ้างอิง ไม่มีแอปจริง ผลตรวจชุดส่งต่อไม่ยืนยัน parser/API/model quality, latency หรือต้นทุน ผล screening เดิมไม่รวมใน starter และไม่ใช้เป็น API benchmark

## Out of Scope

- ZIP ของเว็บอื่น การ scrape สดนอกเส้นทางสินค้าที่ระบุใน intake contract และการค้นเว็บอิสระ
- การประเมินความน่าเชื่อถือผู้ขาย ภาษี ค่าขนส่ง กำไร และหลายหมวดสินค้า
- การรับรองความปลอดภัย การอนุมัตินำเข้า หรือการรับรองว่าตรวจทุกความเสี่ยงครบ
- ระบบตรวจสิทธิ์ในลายแบบเต็ม การพบข้อมูล IP ในเคสนี้ยังไม่ทำให้กลายเป็นงานหลัก
- การส่งข้อความจริง การสั่งซื้อ และการจ่ายเงิน
- การรับคำตอบผู้ขายแล้วประเมินใหม่ เป็นงานเสริมหลังงานหลักผ่าน
- เว็บสาธารณะเป็นงานเสริม ให้เดโม local ทำงานก่อน

## Further Notes

### ข้อเสนอทางเทคนิคที่มีเอกสารรองรับแล้ว

หลังผู้ใช้เลือก TypeScript สำหรับ frontend ข้อเสนอเริ่มต้นเปลี่ยนเป็น React + TypeScript + Vite สำหรับหน้าเว็บ และ Python + FastAPI สำหรับ backend แทนข้อเสนอ Streamlit เดิม เสนอ OpenAI Responses API โดยให้ GPT-6.1 Terra ที่ medium เป็นตัวเต็งและ GPT-6.2 Sol เป็นตัวเทียบตาม ai-execution-plan ทดลองผ่าน Codex ได้แล้ว แต่ยังไม่ได้ยืนยันสิทธิ์ API บัญชี เวลา ค่าใช้จ่ายจริง หรือคุณภาพกับ prompt/schema ของแอป framework และ Interface ยอมรับเป็น Design baseline แล้ว โมเดลเป็นตัวเริ่มทดสอบแบบมีเงื่อนไขตาม AI plan ยังไม่ใช่ผลผ่าน runtime

รุ่นแรกใช้เฉพาะ excerpt DMSC ใน [reference pack](reference-pack.md) เพื่อช่วยตั้งคำถาม ไม่ใช้ตัดสินข้อบังคับนำเข้าหรือรับรองสินค้า มอก./ร่างมาตรฐานและ research notes เดิมไม่รวมในชุดนี้ และไม่เป็นกฎของแอป

### งานต่อหลังยอมรับ Design

- [Ticket breakdown](team-plan.md) ได้รับการยอมรับแล้ววันที่ 19 พ.ย. ใบงาน ready-for-agent สำหรับวันแข่ง งานต่อคือเตรียมเครื่อง/บัญชีและเลือกงานใน fresh Build context ไม่ต้องขยายสเปกเพิ่ม
- ใช้ A/B/C ชั่วคราวได้ ชื่อสมาชิกไม่ขวางการเตรียมงาน ส่วนเครื่องเดโมและสมาชิกจริงต้องกำหนดก่อนเริ่มวันแข่ง
- ตรวจ API/model access, เวลา ต้นทุน การแปล และคุณภาพผลจริงในวันพัฒนา การยอมรับ spec ไม่เปลี่ยนผล screening ให้เป็นหลักฐานของแอป
- Prototype ใน references เป็นภาพอ้างอิงที่จบรอบแล้ว ไม่ขยาย mock หรือย้ายข้อมูลจำลองไปเป็น fallback
- เมื่อถึงวันพัฒนา ให้เลือก ticket ที่พร้อมตาม dependencies จัด implementation plan ของงานนั้นใน fresh Build context ตาม workflow และทำ required reviews/checks ไม่เริ่ม Build จากสถานะ Design accepted เพียงอย่างเดียว

### พรีเซนต์

เปิดด้วยเหตุการณ์จริงที่ผู้ซื้อเข้าใจว่าเป็นงานสกรีน ให้เดโมค้นพบข้อความจากตัวเลือกเอง ถามความต้องการ แล้วแสดงข้อค้นพบที่มีหลักฐานกับเรื่องที่ยังต้องตรวจต่อ แยกวิสัยทัศน์ระยะยาวออกจากสิ่งที่ทำงานจริงในเดโม ไม่อ้างว่าดีกว่า ChatGPT ทางความแม่นยำหรือประหยัดเงินโดยไม่มีผลวัด
